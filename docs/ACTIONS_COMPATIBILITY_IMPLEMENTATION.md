# Actions compatibility implementation packet

Research/design checkpoint: **2026-10-03**. This proposes the next implementation packets for the user's requirement: common GitHub Actions workflows work in Golf, both by explicit manual dispatch and automatically on configured pushes, on the portable and Cloudflare tracks. It is not a new runtime qualification, an approved dependency pin, or permission to enable native Actions in the retained installation. No workflow, external action, provider login, inference, deployment or native fixture ran for this research.

The [implementation plan, section 7](../GOLF_IMPLEMENTATION_PLAN.md#7-actions-and-gitlab-pipeline-compatibility) remains the overall target. [Current execution compatibility](PIPELINE_EXECUTION_COMPATIBILITY.md), [runner isolation](RUNNER_ISOLATION_CONTRACT.md), [automatic grants](AUTOMATION_GRANTS_CONTRACT.md), [push admission](PUSH_AUTOMATION_CONTRACT.md) and [implementation status](IMPLEMENTATION_STATUS.md) define the already implemented boundaries. All packets below are pending until their own runnable evidence exists. Golf's source repositories still receive no CI workflows.

## Decision to implement and why

**Recommendation: retain Golf admission and durable run ownership; use a pinned maintained `act`-based execution component for the expanded Actions catalog.** Stop expanding the small shell compiler into another general workflow interpreter. Qualify the engine before choosing its exact release, image/tool versions and integration boundary. A narrow versioned wrapper can isolate an upstream CLI or internal Go API; the latter must not be treated as a stable public library without a pinned upgrade corpus. The maintained project executes Actions using Docker and dependency-aware workflow planning. [Upstream act](https://github.com/nektos/act).

Reuse engine semantics for expression evaluation, graph expansion, action metadata, step execution and pre/post handling. Golf supplies the durable event/admission identity, current authority, token/secrets broker, allowed dependency resolution, resource/network ceilings, cancellation, receipt journal, storage and UI. Where the engine lacks a feature, either enforce it through a qualified wrapper/control boundary or reject the construct before executing any part of the run. Do not silently strip ignored keys to obtain a green result.

Current `act` documentation lists ignored concurrency, permissions, job timeouts, job environments and several result/UI features; cancellation and OIDC are also gaps. This prevents an engine-only compatibility claim. Its Linux image mappings likewise do not recreate GitHub-hosted runners, and the image/toolchain must be a separate catalog dimension. [Unsupported functionality](https://nektosact.com/not_supported.html), [runner images](https://nektosact.com/usage/runners.html).

Native Gitea Actions plus its runner is a serious alternative to evaluate in packet AC-0, because it already provides a maintained server/runner pairing. The public design describes an external runner, a fork of `act`, registration and distinct runner/job/network paths. [Native Actions design](https://docs.gitea.com/usage/actions/design/). Prefer its supported APIs if they can satisfy Golf's exact-source and policy contracts; do not duplicate a native coordinator behind an unrelated Golf scheduler. The current recommendation selects Golf-owned execution because the required admission fences are already implemented and native automatic scheduling has not been shown to enforce them.

The official `actions/runner` is another reference and potential later adapter; its availability as source does not provide GitHub's server-side workflow orchestration or authorize registering Golf jobs against GitHub. Proving that protocol and backend service surface is a distinct project. [Official runner](https://github.com/actions/runner).

## What works today, exactly

Source basis: the existing `workflow_execution.go`, `workflows.go`, `workflow_runs.go`, `workflow_automation.go`, `runner_transport.go`, `workflow_progress.go` and `internal/runner/execute.go`. The recently qualified exact tree/blob workflow reader replaces SHA-shadowable contents reads; the ordinary archive workspace remains its separate supported snapshot contract.

| Surface | Current implemented catalog `golf.workflow.shell.v1` | Expansion needed |
| --- | --- | --- |
| Source discovery | Direct `.github/workflows/*.yml`/`.yaml`, root `.gitlab-ci.yml`; exact commit/workflow blob and verified bytes; bounded metadata-first inspection | Engine-supported workflow/action dependency discovery with explicit source and version receipts |
| Actions | One Linux job, 1–50 ordered `run` steps, literal names/runner label, omitted/default shell or explicit `sh`/`bash` | Multi-job semantics and common actions; no `uses`, expressions, environments, secrets, matrices, services or reusable workflows today |
| Manual | Input-free `workflow_dispatch` where configured; managed cookie/Origin; current writer and policy; user-scoped original idempotency key | Typed inputs, per-workflow/pool controls, richer engine plans and explicit original-outcome inspection |
| Automatic push | Verified native event plus independently delegated sponsor grant, allowed branch/workflow paths and exact event commit; push and manual ceilings are separate | Tag/glob/path filters, larger event catalog and maintained-engine workflow admission |
| GitLab | One digest-qualified image/job with one shared script; explicit Golf branch-push mapping | Native GitLab graph/rules/coordinator/Runner compatibility remains separate from Actions |
| Runtime | Dedicated Docker executor/daemon, operator-approved existing image digest, no job network or host Docker socket, resource/output/time limits | Controlled dependency network, full Git checkout, job/service/action containers, more qualified pools |
| Lifecycle | SQL ownership/leases/fences, current policy/credential checks, durable cancel/outcomes, ordered bounded logs and independently enrolled-worker step events | Multi-job/matrix records, artifacts/cache, rerun histories, service-backed actions and capacity qualification |

Manual-only, push-only and both-enabled workflows must remain independently usable. `on: push` does not create a manual dispatch event; a disabled manual button is correct for push-only YAML. Conversely, manual permission must not activate automatic push. GitHub documents distinct event declarations; Golf's policy intersects the declared event rather than rewriting it. [Workflow events](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#on).

The existing [push proof](../scripts/push-ci-smoke.py) performs actual Git pushes and verifies signed intake, exact commit/blob, disabled-intake non-revival, sponsor/logout independence, deduplication, restart, revocation, execution and cleanup. It is evidence for the current shell catalog only. The isolated CI/all-page captures have their own image/manifest provenance in [route coverage](ALL_PAGE_ROUTE_COVERAGE.md#actual-served-audit-checkpoint).

## AC-0: engine and native-adapter feasibility before expansion

Complete this bounded packet in a fresh disposable stack; retained native Actions remains disabled until an explicit deployment/configuration task follows successful proof.

| Candidate | What to prove | Select or reject criterion |
| --- | --- | --- |
| Pinned `act` execution with Golf coordinator | Exact workflow/action bytes; independent manual and push event payloads; Linux jobs/needs/matrix/conditions; supported structured job/step observations; hard kill/cleanup; no ambient credentials; dependency network mediated outside jobs | Select if known ignored fields can be enforced or refused, action/source provenance remains exact and progress cannot be forged by source stdout. Start with one workflow attempt in an isolated executor to qualify engine semantics; scaling across workflow attempts is useful immediately |
| Native Gitea Actions + pinned compatible runner | Supported workflow/run/job/log/artifact/registration APIs; declared event behavior; exact-SHA dispatch and receipt; workflow disable; sponsor/current role/policy revocation; effect-safe unknown dispatch; cancellation; one execution owner | Select only if native admission cannot bypass Golf policies through a direct push/API and native outcomes can be bound to the original Golf intent. A wrapper that observes already-started unauthorized jobs is insufficient |
| Official GitHub runner protocol adapter | Real supported task/authentication/result/artifact/cache interfaces, backend obligations and maintenance ownership | Later option only after explicit feasibility/cost decision; do not substitute a simulated job for a registered protocol proof |

Pinned installed **Gitea 1.27.3** OpenAPI includes repo workflow list/get/enable/disable/dispatch, runs/attempts/jobs/logs, rerun, artifacts, secrets/variables and runner registration/management. The local read-only inventory `/tmp/golf-gitea-route-inventory/swagger.v1.json` matches [versioned API documentation](https://docs.gitea.com/api/1.27/). It exposes **no Actions run-cancel endpoint** in that inventory. Do not invent cancellation through direct database writes, internal repository edits or an undocumented web mutation.

Pinned dispatch schema requires `ref` and accepts string-valued `inputs`; `return_run_details` is an optional supported query, with 200 and 204 success responses documented. That is a useful receipt path to test, not proof of Golf idempotency. Native dispatch is not assumed to accept a full commit simply because a `ref` field exists. AC-0 must characterize accepted refs, branch movement, workflow selection, response identity, timeout/lost acknowledgement and effect-count readback. If a POST can have taken effect without a recoverable exact receipt, preserve uncertainty and prevent fresh-key replay; do not find a run by similar title/time and adopt it.

Versioned native 1.27 documentation describes environment, expression, runner-label and annotation gaps, plus different token scopes. Latest unversioned runner/docs can describe newer behavior. Bind tests to **forge version + runner version + engine commit + runtime image + action commit + API profile**, never just a product family name. [Gitea 1.27 comparison](https://docs.gitea.com/1.27/usage/actions/comparison/), [current Gitea Runner docs](https://docs.gitea.com/runner/2/).

Deliverables: short engine ADR, exact pins/licenses/SBOM, enforce/refuse feature table, conformance harness, lifecycle/authority matrix and upgrade policy. If none passes, leave the expanded catalog unavailable and report the failed contract instead of adding a compatibility badge.

## Execution and authority contract to preserve

1. Admission resolves native repository/owner IDs and exact source commit before planning. Persist workflow path/blob/digest, event origin/ref/payload fingerprint, manual actor/session **or** push sponsor/grant revision/epoch/credential binding, selected policy epochs, engine/action/image identities, pool/resource limits and original operation key. Friendly branch names remain routing/event context, not a source lock.
2. Freeze the engine input and resolved dependency graph. Action refs may be user-readable tags, but the admitted execution records actual immutable commits/digests. A changed tag/cache lookup cannot replace an accepted dependency during retries or later jobs. Cross-project private actions/reusable workflows require current producer and consumer authorization; no generalized site-admin credential substitution.
3. One durable coordinator owns each run. Before every assignment, token/secrets issuance and accepted result, check the applicable session or sponsor grant, native identity/access and policy epochs. Revocation cancels/fences remaining work and denies new credentials. The engine parser's accepted plan grants no authority.
4. Preserve once-only dispatch intent and explicit attempts. Losing a lease, backend acknowledgement or native response must not restart potentially executed work. Safe preparation reads may retry under bounds; execution/rerun is a separately authorized action with a new attempt and original causal link. Source steps can themselves call external APIs, so job execution is not inherently idempotent.
5. Keep trusted worker/engine observations separate from source stdout. Structured engine hooks/events enter Golf through enrolled worker transport bound to run/job/matrix/attempt/lease. `::error`/annotations and command files are source-controlled output, not trusted completion or protection evidence.
6. Persist private data under deliberate credential/content domains. Metadata journals contain identities/fingerprints/status, not plaintext secrets/private scripts. Source, output and artifacts require current scoped read authority. Logs are redacted before durable storage and streaming, with chunk-boundary cases tested; masking is not a guarantee against deliberate exfiltration.
7. Native reported statuses and ordinary green workflow results remain distinct from trusted required-check/merge authority. P0.8/protected merge cannot be completed by importing an engine, forging a familiar check name or running only the PR head instead of the actual candidate.

### Checkout, tokens and service endpoints

The first unchanged upstream target remains [Requests lint.yml at611c616](https://github.com/psf/requests/blob/611c6162cbc4ac2020a2f91c7cfa4f3abf9bbb60/.github/workflows/lint.yml). Its pinned [checkout URL helper](https://github.com/actions/checkout/blob/9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0/src/url-helper.ts) uses the configured origin plus `/OWNER/REPO`, discarding any `/git` path prefix and omitting `.git`. Its [authentication helper](https://github.com/actions/checkout/blob/9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0/src/git-auth-helper.ts) sends Basic `x-access-token`. Golf's human Git path and `golf` username therefore cannot be substituted merely by changing `GITHUB_SERVER_URL`.

The first [trusted runner-only exact-commit preparation source packet](RUNNER_GIT_PREPARATION_CONTRACT.md) now reuses enrolled-worker/attempt/current source and policy fences, with real PostgreSQL/race and separate installed-Git negotiation proof. Actual native-to-worker checkout integration and deployment remain open. The worker capability remains outside jobs because it also authorizes logs and completion. Unchanged checkout needs a separately scoped read-only job token and compatible checkout-origin routes, with no human-session, sponsor/native PAT or worker-control credential exposed. Qualify actual detached HEAD/tree/workflow bytes and credential removal before claiming a full workspace. Pinned remote Node24 action acquisition/runtime, the original push/PR declarations, contents permissions, job timeout and restricted dependency egress remain independent requirements; none can be enabled by relaxing the existing inspector.

These often determine whether real imported workflows run, even when syntax parses:

| Boundary | Proposed supported behavior / gate |
| --- | --- |
| Full Git workspace | Per-attempt clone/fetch using supported Git transport, detached checkout at admitted exact object, independent HEAD/tree/workflow-blob verification, controlled fetch-depth/tags and exact objects retained for the attempt. LFS/submodules require separate scoped credential/network/path/cleanup proofs. Current archive snapshot is not advertised as full checkout |
| `actions/checkout` | Test exact selected versions against Golf/Gitea reachable Git URLs, repository IDs and credentials, `github-server-url`, SHA/ref/event behavior, alternate path, checkout cleanup and credential persistence. GitHub-specific REST fallback remains blocked until a real supported endpoint is implemented. No silent action substitution |
| Job token | Issue a short-lived, job/attempt-scoped Golf token whose granted endpoints are explicitly cataloged. Clamp workflow/job permissions against instance/owner/repo/fork/environment policy; never expose browser cookies, sponsor PATs, admin/runner-control credentials or another tenant's provider connection |
| `GITHUB_SERVER_URL` / API / GraphQL | Set truthful platform URLs and separately publish compatible endpoints. A native `/api/v1` endpoint is not GitHub `/repos/...` REST compatibility; Golf Connect/gRPC is not Octokit REST/GraphQL. API-dependent actions need a narrow authenticated adapter or remain unsupported, with no transparent cross-host token/URL rewrite |
| Git writes from jobs | Distinct explicit write grant and endpoint support with trigger recursion/actor causality safeguards. Read checkout cannot inherit permission to push branches, edit workflows, merge or dispatch another run |
| Secrets/variables | Encrypted versioned inventories at instance/owner/org/repo/environment scopes, deliberate precedence, current authorization at issuance and audit of metadata-only use; untrusted fork rules explicit. Imported secret names never auto-create credentials or prompt plaintext artifact capture |
| OIDC | Golf issuer/audience/claims/JWKS, job identity/expiry and scoped cloud trust; never claim GitHub issuer identity. Deny `id-token` until the actual issuer and least-privilege destination policy are qualified |

Checkout versions have differing runtime/credential behavior; the currently consulted README describes Node24, credential persistence and newer fork safety changes. Pin the admitted action commit and test those behaviors instead of assuming `@v4` examples establish all versions. [actions/checkout](https://github.com/actions/checkout). GitHub's token lifecycle/permissions are a semantic reference, not a credential Golf already possesses. [GITHUB_TOKEN authentication](https://docs.github.com/en/actions/tutorials/authenticate-with-github_token).

### Artifact/cache adapters

`act` has an opt-in local artifact server, with limited same-run action support and a documented cross-run limitation. That is useful for AC-0, not a multi-tenant Golf artifact service. [act artifact support](https://nektosact.com/usage/#action-artifacts). Artifact protocol generations differ, including the toolkit's backend changes and current GHES caveat; cache similarly has a newer service protocol and action/runtime requirements. [Artifact toolkit](https://raw.githubusercontent.com/actions/toolkit/main/packages/artifact/README.md), [cache action](https://github.com/actions/cache).

Implement version-tested artifact create/upload/finalize/list/download/delete and cache reserve/upload/commit/lookup/download profiles needed by selected actions. Issue attempt-scoped runtime URLs/tokens rather than global bucket credentials; validate job/repo/run ownership at each request and object digest/size at finalize. Use RustFS/S3 locally and R2 on the Cloudflare track behind the same domain contracts. Object storage alone does not implement Actions artifact/cache APIs.

Artifacts are immutable named run/attempt outputs with actual IDs/digests and bounded archive extraction/download, retention and permissions; test duplicate-name/finalization/replay and cross-run/cross-repo reads. Cache keys/version/ref/trust/pool scopes and ordered restore matches need explicit semantics, size/retention/eviction and concurrent writer rules. Untrusted fork/PR output cannot poison privileged default-branch or deployment caches. Distinguish cache miss from denial/unavailable service; do not announce success after a dropped upload. Action-reported annotations/summaries/artifacts remain untrusted content, with sanitized rendering and current private-read checks.

## Two tracks, one Actions contract

| Function | Portable defaults and scalable choices | Cloudflare-focused choice and qualification gate |
| --- | --- | --- |
| Admission/run truth | Golf/PostgreSQL durable plans/attempts; remote PostgreSQL supported profile when qualified | Same logical identity/authority boundary; optional Workflows orchestration only with a single recorded owner for a run |
| Delivery/capacity | Existing SQL queue; worker pools on dedicated Docker hosts, then Kubernetes Jobs/qualified VM pools with registration/capacity/quotas | Queues for buffering/fanout; Durable Object per run/pool identity where useful. Duplicate delivery must call Golf idempotent admission, never directly execute source |
| Linux execution | Qualified pinned engine plus dedicated daemon/microVM first; full workspace/service/action container profile | Sandbox/Containers adapter with exact image/job identity, credential/network isolation, deadlines, cancellation/cleanup and quotas. Workers/Dynamic Workers are not Linux/Docker executors |
| Storage | RustFS local; arbitrary qualified S3 profiles, bounded manifests/digests/retention | R2 source/artifact/cache objects; scoped Worker/broker endpoints. No shared writable filesystem-as-cache assumptions |
| Credential/egress broker | Golf service endpoints with least-privilege job tokens and approved dependency mirror/registry network | Worker-mediated access, scoped bindings/egress controls and resource cost visibility; original tenant/provider credentials withheld from source unless explicitly granted |
| Result/live UI | Existing authorized event invalidation/log contracts, registered worker evidence | Same result fences and private stream behavior, regardless of which CF delivery/execution resource produced the observation |

Cloudflare's current Sandboxes documentation distinguishes full Linux container environments from Dynamic Workers and describes Worker-controlled application/network access. Containers provide programmable Linux image instances. Those facilities justify a real executor investigation; they do not establish Docker Actions, service containers or nested daemon compatibility. [Sandboxes](https://developers.cloudflare.com/sandbox/), [Containers](https://developers.cloudflare.com/containers/). A Docker-in-Docker guide exists under the **SDK 0.x** documentation; validate current SDK/runtime support and security rather than assume an old example is an approved modern executor. [Versioned Docker guide](https://developers.cloudflare.com/sandbox/sdk/guides/docker-in-docker/).

Workflows offer durable waits and retries; Queues offer at-least-once delivery. Deduplicate preparation and admissions, explicitly disable unsafe execution/promotion retries, and retain unknown outcomes. A CF provider step must not duplicate a SQL-owned execution attempt. [Workflows](https://developers.cloudflare.com/workflows/), [Queues delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/).

Hybrid is a first-class outcome: a Compose/Kubernetes installation may use R2 only, or CF orchestration with qualified remote Docker/Kubernetes executors. If an account cannot safely run the full Linux/Docker profile on CF, advertise its real mixed profile rather than claim the whole platform runs inside Workers. Linux profile support does not imply macOS/Windows runner availability; those require separately owned pools and explicit catalog entries.

### Required conformance corpus

Store owned source fixtures outside `.github/workflows` in Golf's repository so no source-repository CI activates. Each case records original bytes/digests, event/context, allowed catalog/version/pool/policy, expected effects or preflight refusal, native/resource observations and cleanup. When importing public example repositories, record exact upstream commits/license and never run an unreviewed third-party workflow just because it is public.

| --- | --- |

| Graph/expressions | independent jobs, `needs` diamond/failure/skip, `always`/`cancelled`, matrix include/exclude/dynamic JSON/expansion limit, max-parallel/fail-fast; null/string/number/boolean coercion, context availability and workspace hashFiles |

| Lifecycle/scaling | cancel queued/running/parallel jobs and service/post work, timeout, explicit rerun, worker crash/lost result, SQL acknowledgement loss, restart/two replicas, revoked session/grant/native role, stale attempt and capacity/budget fences |
