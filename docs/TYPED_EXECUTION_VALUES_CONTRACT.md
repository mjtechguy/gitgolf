# Typed manual execution-value approvals

Schema060 adds an exact-input approval consumer for maintained Actions v2 manual execution (`golf.workflow.act.v0.2.89.linux.v2`). This is source implementation and source/PostgreSQL qualification. Actual schema060 native/Docker execution, certificate-verified TLS worker delivery, served approval UI and latest-schema recovery have not been qualified. Existing historical v1 and typed input-free-value proofs keep their original scope. Full Secrets and Actions acceptance requirements in [repository settings](REPOSITORY_SETTINGS_IMPLEMENTATION.md) remain open.

## Explicit approval and immutable identities

The repository Secrets and variables page opens an editor only after **Add approval** or **Edit**. Legacy v1 remains the default for new approvals. Selecting **Exact typed manual input set** requires a full commit SHA, one supported workflow path, a manual event with empty push ref, expiry and up to 64 distinct current scoped value versions. The editor inspects the exact repository ID and full SHA, then opens the shared four-type input form. Editing a historical typed approval requires a fresh reviewed input set; no prior input body is reconstructed or revealed.

Before approval, `PrepareWorkflowDispatch` independently resolves exact source and declaration defaults and returns the contract `golf.workflow.dispatch.inputs.v1`, workflow blob ID, schema SHA256 and canonical submitted/effective SHA256. The browser validates native repository/owner/actor IDs, full commit/blob widths, path, schema and identical declarations. Only a further explicit approval submits the fresh input values with those claims. It performs no dispatch and grants no CI policy, push sponsorship or provider capability.

`SaveRepositoryExecutionBinding` adds `inputs` (field12), optional `input_contract` (13), `workflow_blob_id` (14), `schema_sha256` (15), `submitted_sha256` (16) and `effective_sha256` (17). Entire absence preserves the legacy v1 contract; an explicitly empty optional contract or a partially populated typed identity is refused. Canonical submitted maps preserve presence: omission/defaults, explicit false, zero and empty strings remain distinct. Submitted expression-looking strings are literal data. The server independently reparses source and validates types, defaults, canonical maps and digests before acceptance; client digest reuse cannot authenticate changed values.

The immutable approval version freezes the four input identities in addition to its existing repository/owner, workflow path, full H/blob, archive hash, engine catalog, manual event, scoped value IDs/versions, approver, session and expiry. Inventory returns only the four digest/contract fields, never input maps. Approval operation metadata contains those identities and existing intent metadata, no input bodies or secret-derived hashes. Legacy operation JSON retains its original field order/shape via omitted new fields, so historical original-key replay stays valid.

## Release, revocation and private results

Typed dispatch still uses the authenticated encrypted schema059 input payload. The v2 run must exactly match the approval catalog, input contract, schema and submitted/effective digests as well as existing source and scoped value identities. A v1 approval cannot match a v2 run, and a changed/defaulted input set requires a fresh approval. The release consumer independently revalidates retained source/schema/maps/digests and existing current actor/session/admin authority, expiry, local and organization value approvals, same-organization ownership, value versions, active keys and lifecycle fences.

Claim/release requires the maintained Actions worker capabilities and typed protocol over the existing HTTPS/TLS1.3 boundary. Source tests that set a request TLS version do not establish a certificate handshake; that remains an actual runtime qualification. The worker and engine retain their independent exact event-string/typed-input and environment validation before effects. No input-driven image/resource/graph authority or secret-expression context is admitted. V1, legacy GitLab shell and push behavior remain unchanged; input-declaring v2 push, fork, shell, agent, deployment, environment and OIDC consumers remain unsupported.

Existing encrypted output quarantine, verified-completion checks and cross-chunk exact-secret masking apply. Approval/value replacement or removal fences affected queued/running attempts; logout, expiry, account/native-admin loss and organization sharing changes withhold further release. Transformed secrets are not guaranteed detectable. No new encrypted family or plaintext journal is introduced: the existing 13 crypto families and their startup/count/rotation/retirement/recovery accounting are unchanged.

## Lost acknowledgement and bounded transport

Before its single save, the browser persists only original operation/key/target/version/broker metadata in session storage. Input bodies remain volatile. Accepted response loss, transport failure or missing original status never triggers an automatic resend. Reload offers only explicit original operation inspection. An exact historical receipt releases local uncertainty for a separately reviewed new action; denial/revalidation clears private inventory and editors, and late preparation cannot write or restore text after a scope transition. Save/replay follows existing current-authority, CAS and original-key fingerprint checks.

Only the managed `SaveRepositoryExecutionBinding` procedure accepts a 64KiB encoded JSON body; neighboring procedures retain their existing bound. This transport allowance is distinct from canonical input bounds (25 declarations, 2048 bytes per value, 8192-byte canonical submitted/effective maps) and the 64 scoped-reference bound. Escaped JSON can exceed raw text length. Oversized or malformed envelopes are refused before effects; no metadata endpoint releases input maps or values.
