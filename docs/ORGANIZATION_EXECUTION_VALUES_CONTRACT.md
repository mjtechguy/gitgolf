# Organization execution values: selected-repository scope

This is the ORG-Values-1 implementation contract. The source packets define migration052, browser-only organization value methods, encrypted immutable content/policy, scoped repository approvals and release fences, and encryption lifecycle accounting. **Source integration is not deployment or runtime qualification.** Routes/client mounts, served UI and actual selected-repository runner execution are separate gates. The full [Secrets, variables and OIDC](REPOSITORY_SETTINGS_IMPLEMENTATION.md) and environment requirements remain required. Schema051 belongs to managed Git and is unchanged.

## Existing boundary and the selected increment

The existing repository broker stores immutable encrypted values and session-backed approvals of exact repository, workflow path, full commit/blob, source archive digest, maintained Actions catalog and manual/push event. Only that maintained Actions consumer receives values as execution environment variables. Policy, push sponsor and runner enrollment remain separate authority. Secret-bearing output is withheld and retained encrypted until qualified terminal redaction. Shell catalogs, agents, production, fork approvals, context expressions and OIDC do not gain access from this extension.

The selected increment adds organization-owned values shared with explicitly selected current repositories of that same organization. It does not add automatic all-repository sharing, an organization team administration role, named execution environments, job-scoped protection or provider deployment credentials. A named environment needs a real job-bound release/protection gate: the current repository consumer delivers its environment to the whole admitted Actions attempt.

GitHub's [organization secret policy](https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets) distinguishes organization ownership, selected-repository access and repository/environment consumers. Golf follows those scope distinctions while retaining its stricter exact-source broker contract.

## Browser methods and observations

`OrganizationExecutionValueService` exposes five managed browser methods; no delegated bearer/API/CLI/MCP authority is added:

- `ListOrganizationExecutionValues({target})` returns exact target, broker revision, metadata values, 64 retained-name cap, 20 selected-repository cap and the existing maintained consumer profile. It does not return secret content.
- `SaveOrganizationExecutionValue({target,id,expectedVersion,expectedBrokerRevision,operationId,name,kind,value?,selectedRepositories,expiresAt})` creates/replaces an encrypted content+policy version. Missing `value` is permitted only for editing an existing nondeleted value's policy; it decrypts that value solely on the server and seals a fresh immutable version. It cannot create or restore unspecified content.
- `DeleteOrganizationExecutionValue` requires the exact ID/current version/broker revision/original operation ID and writes a retained tombstone. Encrypted history remains.
- `GetOrganizationExecutionVariable({target,id,version})` reveals only the current nondeleted VARIABLE version to a current actual organization owner. SECRET has no readback endpoint.
- `GetOrganizationExecutionValueOperation({target,operationId})` reads only the caller's original metadata receipt after current authority checks.

Target is `{organization,organizationId}`. A selected repository is `{repository:{owner,name},repositoryId}`. Organization/repository IDs are canonical positive signed64 decimals; item/operation IDs are canonical UUIDs. Names/kinds/bodies reuse the existing execution-value validator. Selection is bounded to 20 distinct IDs and distinct case-insensitive routes; foreign organization names, replaced IDs, archived/mirror targets and changed native owners are refused. Empty selected repositories is valid and grants no repository access.

Save bounds are 64 retained names per organization, 256 encrypted content/policy versions, the existing active environment byte aggregate, 8 KiB single-line bodies (secrets at least 8 bytes), and expiry between one minute and 30 days, before the approving session expires. PostgreSQL stores microsecond expiry precision; encryption binds that stored observation, while the operation fingerprint preserves the exact original expiry string.

Value metadata includes the existing ID/name/kind/current version/deleted/created/updated fields plus the selected repository observations, share expiry and `requires_current_authority`. That label is a condition, **not a successful ongoing permission/health check**. Historical selected route names can become stale after rename/transfer and do not establish present authority.

## Identity, original intent and authority

Native supported reads independently establish current caller identity, 204 organization membership, exact organization ID and explicit `is_owner:true`. Golf/site administration, public metadata or inherited effective owner-like repository permission supplies no substitute. Native identity/organization/owner proof is rechecked after SQL waits and after successful operations. A lost or denied postcommit acknowledgement can leave a durable accepted receipt; it does not imply rollback or permission to resend.

Mutation lock ordering is managed users/session, sorted affected repository lifecycle gates, organization broker, then existing repository broker/run dependencies in the consumer packet. Old and new selected repository IDs participate. The current policy is reread after the broker wait; an uncaptured changed selection refuses the request rather than acquiring out-of-order gates. Concurrent creates/edits serialize on one organization broker revision. Inventory locks the same broker without creating an absent scope, so its revision and collection cannot mix competing saves.

The metadata journal stores action, immutable target/item, expected versions, name/kind, optional-body presence, original ordered selected IDs/routes, original expiry and accepted receipt/time. It stores no body or secret-derived body hash. Exact-key replay compares complete metadata and, when content was supplied, compares that content against the encrypted accepted version in constant time. Reordering an otherwise equal selected set, changing optional-body presence/content, expiry or other intent is a different request and is refused. An exact replay performs no mutation and cannot renew the original share expiry/session authority. Status and replay remain historical receipts, never a new release grant. Current organization ownership and the caller's managed session are required for inventory, variable reveal, replay and status.

Save/revoke metadata is private. It emits no shared repository activity revealing secret names, organization values, recipients or operation existence. Consumer cancellation/release events remain separately scoped under their existing execution contracts.

## Storage and encrypted identity

Migration052 adds four tables: organization brokers, current value metadata, immutable content+policy versions, and immutable actor-scoped metadata operations. It does not store a native provider token or fabricate a repository identity for organization scope. IDs/name/kind/scope remain immutable; each update advances the current metadata version once. Delete advances metadata and retains earlier ciphertext. Restore needs explicit replacement content.

The organization-specific encryption domain is `organization_execution_value`; its AAD binds item/version, configured forge, exact organization ID, name/kind/byte count, complete ordered selected policy, local/native approver IDs, hashed approving session and normalized expiry. Repository-domain ciphertext cannot be transplanted. The active-key insertion guard and immutable ciphertext identity triggers preserve existing key activation and rotation semantics. Only ciphertext and key label may change during rotation.

The source integrates organization rows into the existing execution-value-family paths: distinct `organization_execution_values` operator usage counts, `rotated_organization_execution_values` rotation receipts, `organization_execution_values_count` crypto events, startup required-key/fingerprint accounting, legacy bootstrap validation, remaining-use totals, bounded rotation and retirement refusal. Scans include every immutable encrypted history version, including tombstoned values and removed selections. Rotation keeps policy/AAD/version unchanged and updates only ciphertext and key label.

Coordinated backups use the complete Golf database dump, which includes all four new tables and the additive crypto audit column. Keep every key required by captured ciphertext and historical backups. Existing offline recovery deletes restored managed sessions, disables local accounts and cancels queued/running work. Organization approving session hashes remain historical metadata; their absent sessions cannot authorize release or silently become valid when an account is re-enabled. Prepared source-PG tests assert preserved ciphertext/receipts and denied release after this operator invalidation. **No migration052 encrypted backup/fresh restore drill has run**; that full recovery acceptance remains open.

## Scoped consumer and required UI

The additive consumer contract is `RepositoryExecutionValueReference.scope` (legacy absent means repository; explicit REPOSITORY or ORGANIZATION) plus `organizationId` required only for inherited references; repository inventory gains metadata-only `inheritedValues`. Exact binding references freeze origin, ID and version. Existing repository-owned values of the same name/kind are explicit overrides; UI identifies both origins and the selected winner. Cross-kind name collision refuses rather than silently turning a secret into a variable. A new local override invalidates prior inherited approvals for that name.

The common broker helpers used by admission, claim, heartbeat, release and terminal output handling independently retain both current authorities: the organization owner's approving managed session/expiry/native actual-owner proof and the repository source approver's current administrator/session proof. Repository owner ID must still equal the pinned organization ID, with current native source identity and same-org selection. Content replacement, deletion, policy removal/change, session expiry/logout/disable, org ownership loss and repository transfer deny subsequent release. The existing consumer/quarantine machinery counts and redacts all selected winning secrets, never an implicitly merged duplicate name. Scoped selections include one to 64 distinct immutable IDs/versions, subject to the existing 8 KiB encoded reference bound; PostgreSQL JSON whitespace overhead is conservatively reserved before admission. Repository and organization IDs are separate scoped identities even when a caller chooses the same UUID; cancellation binds the owning organization/scoped reference and cannot revoke another tenant or scope. Legacy absent scope retains its original repository serialization; explicit scope and organization identity are part of immutable operation intent.

Consumers prelock the actor, repository source approver and all organization share approvers in one sorted unique local-user order. They then acquire lifecycle gates, organization broker (including absence), repository broker and existing policy/run locks. Native approving credentials are resolved before these locks. After waits, managed session/CV checks and exact immutable share metadata are repeated; supported native actual-owner and same-org repository receipts use the request-local credential without refreshing OAuth under held identity locks. Independent pre/postflight reads recheck expiry/version/selection and native identity. These observations do not establish atomic native permission/source edits with SQL, ref fencing or freedom from an external ABA change.

Creating a same-name/same-kind repository override invalidates inherited-bound queued/running attempts; it does not rewrite or renew earlier bindings. A cross-kind override/share selection is refused. Deleted local values do not automatically rewrite old approvals to inherit again. A new explicit binding must select the desired scoped immutable version. No automatic value merge or fallback occurs.

Organization settings show metadata inventory and explicit Add/Edit/Replace actions. Repository settings show inherited source, selected access/expiry and explicit Override action. Requested TanStack forms/shared tables/global CSS, metadata-only original operation storage, scoped private query cancellation, late-account/denial clearing, and current-source receipt validation remain mandatory. No permanent bare form or secret body in browser storage.

## Evidence and remaining gates

The packets include pure source tests for exact selected identities, organization-owner proof, org-bound ciphertext/AAD/domain separation and mutation admission. Disposable PostgreSQL tests are prepared for create/policy edit/delete history, original-key fingerprint/replay, omitted versus explicitly empty content, normalized expiry/AAD, current-variable-only reveal, current authority after broker waits, native target replacement and browser boundary denials. Consumer tests cover exact inherited release, explicit same-kind override versus cross-kind refusal, queued/running cancellation on override/selection removal, current owner/selected organization/session/CV loss, historical key counts, corrupt legacy bootstrap, bounded rotation/retirement and preserved-but-disabled recovery history. Without a configured test DSN these tests skip; an ordinary passing source command is not real PostgreSQL proof.

At source freeze there is no actual org-shared runner execution, served UI, migration052 recovery qualification, named environment protection or workload identity proof. Root owns resource-backed qualification. Required consumer tests include actual selected/unselected/foreign/transfer/fork denials, dual authority loss at every release boundary, competing override/share changes, exact source/version pinning, late failure quarantine, cross-chunk redaction, retained key rotation/retirement, and browser loss-of-acknowledgement inspection without resending content. Environment/job scope, non-Actions consumers, context expressions, durable background consent, CLI/MCP parity and OIDC remain explicit follow-up requirements rather than a complete Settings row.
