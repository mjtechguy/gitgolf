# Repository experience parity workstream

This workstream preserves the full GitHub-like collaboration objective in Golf's own brand. The previous goal turn made verified progress: managed advisory PR reviews are implemented and live-qualified. It did not complete repository UI parity.

## Evidence and product boundaries

References inspected 2026-10-03: [GitHub README behavior](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes), [PR review workspace](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request), [review semantics](https://docs.github.com/en/pull-requests/reference/pull-request-reviews), [Gitea collaboration](https://docs.gitea.com/usage/issues-prs/), [Gitea Actions differences](https://docs.gitea.com/usage/actions/comparison/). These define reference behavior, not evidence of implemented Golf features. Reconcile API inventories against the pinned native version before writes.

Existing source, commits, issues and PR pages mostly expose read-only records. Native issue create/comments and managed bot COMMENT reviews exist. Commit diffs now use the shared structured file/hunk viewer, with native-text fallback for unsupported formats. PR Files changed is also implemented as a selected base/head observation. Manual/push shell CI exists with a deliberately bounded compatibility catalog. Actions now exposes workflow execution and coding tasks; their policies/configuration remain in repository settings. Merge/checks remain subject to the unresolved P0.8 integrity gate; do not silently expose an unfenced protected merge API or redefine parity to omit merging.

## Execution model

Actions is the user-facing automation workspace, not the name of one runtime. CI jobs and coding/review tasks retain distinct immutable receipts, authority/policy, credentials, budgets and executors while linking to the same repository and commit. Local Docker/Kubernetes runs coding CLIs in isolated containers/Pods. Cloudflare Workers/Queues can coordinate work and Containers or another explicitly configured compute backend can execute CLI tasks. A Worker is not required for the portable track and does not by itself run arbitrary coding CLIs. Cloudflare logs, D1/Postgres/R2/Queues/Containers adapters require their own qualification; an Actions tab does not establish them.

## Acceptance and tracking

For each row retain files/API contracts, actual native API coverage, pending work and exact evidence in IMPLEMENTATION_STATUS.md. Run positive/denied/private-fork/stale-head/reconnect tests against actual owned local fixtures. Never run imported public workflows blindly. No CI workflows are added to Golf's own repository. Keep the goal active until every applicable capability, layout requirement, live transport, agent-log contract and Actions qualification is verified; a successful UI foundation is progress, not parity completion.
