# Forgejo portable setup and migration status

The Forgejo destination is implemented as a separate qualification profile.
**Existing Gitea installations have not been migrated, and the default has not
been flipped.** The [transition plan](FORGEJO_MIGRATION_PLAN.md) remains the
release gate. Cloudflare-native keeps Artifacts/D1/Workers.

## Fresh local/Docker destination

```sh
make forgejo-setup
make forgejo-up
# Stop when finished; preserves this destination's data.
make forgejo-stop
```

This uses `compose.forgejo.yaml`, project `golf-forgejo`, and a private
`.env.forgejo`. The initializer never replaces an existing environment file.
Golf listens at `http://localhost:8380`, Forgejo at `http://localhost:3301`, and
SSH at port 3222. Bindings are loopback-only. Configure HTTPS and secure cookies
before exposing the installation remotely.

The destination has independent PostgreSQL and Forgejo volumes. Do not merge
this Compose file over an existing Gitea project, override its project name to
the source's project, attach old volumes, or point it at the source databases.
Forgejo's actual rootless image uses `/var/lib/gitea`, with configuration at
`/var/lib/gitea/custom/conf/app.ini`; these are upstream path names.

Create the initial provider administrator with the native CLI, then enroll its
scoped provider credential through Golf's existing `local-account` command:

```sh
docker compose -p golf-forgejo --env-file .env.forgejo -f compose.forgejo.yaml exec forgejo \
  forgejo --config /var/lib/gitea/custom/conf/app.ini admin user create --help
```

Follow [local authentication](LOCAL_AUTHENTICATION.md) for Golf enrollment;
use the Forgejo Compose command above in place of the old project command.
Credentials belong in private stdin/environment inputs, never committed files.
Native Actions remains disabled. `compose.ci.yaml` can be used with this fresh
profile after explicit runner enrollment; Golf continues to own scheduling.

For a host-run Golf binary use the same PostgreSQL/keyring setup and the neutral
configuration below. Existing local HTTPS, storage, recovery and Kubernetes
operator procedures must not be assumed qualified merely because Docker works.

## Configuration and compatibility

| Neutral setting | Transition alias / behavior |
| --- | --- |
| `GOLF_FORGE_KIND` | `forgejo` for the new destination; omitted retains `gitea` |
| `GOLF_FORGE_INSTANCE_ID` | Required stable lowercase UUID v4 for Forgejo; generated by setup |
| `GOLF_FORGE_URL` | `GITEA_URL` |
| `GOLF_FORGE_PUBLIC_URL` | `GITEA_PUBLIC_URL` |
| `GOLF_FORGE_OAUTH_CLIENT_ID` | `GITEA_OAUTH_CLIENT_ID` |
| `GOLF_FORGE_OAUTH_CLIENT_SECRET` | `GITEA_OAUTH_CLIENT_SECRET` |
| `GOLF_FORGE_WORKFLOW_DIRS` | `GOLF_GITEA_WORKFLOW_DIRS` |
| CLI `GOLF_FORGE_TOKEN` | `GOLF_GITEA_TOKEN`; independent of Golf API/native workspace tokens |

Conflicting aliases fail without printing their values. Public RPC names/field
numbers and `/auth/gitea/callback` remain stable for existing clients. Register
that callback when enrolling a new Forgejo OAuth application.

Schema 095 binds the selected kind, URL, installation ID and workflow order to
the Golf database. Startup and mutating local-account administration reject a
changed binding. A fresh Forgejo binding refuses pre-existing unmapped Golf users.
There is no general-purpose rebind command yet. Do not work around the fence by
editing the table or dropping historical users. An installation ID is operator
configuration, **not remote cryptographic attestation**: replacement of a server
at the same URL while retaining its configured ID remains a qualification gap.

Forgejo's initial workflow selection is `.forgejo/workflows`, `.gitea/workflows`,
then `.github/workflows`; the first existing directory wins. Shadowed directories
are reported, and only the selected directory can execute. Literal filename,
immutable source, permission, policy and revocation checks still apply. Existing
Gitea installations keep their two-directory default. Changing a bound order
requires a qualified re-admission path; it does not silently switch execution.

The qualified image is
`codeberg.org/forgejo/forgejo:15.0.9-rootless@sha256:caf1bca332f95cdcf124227a4bfa3b49bbbfbbc8a5e4a97406921cb581165413`.
Qualification here was Linux amd64. Readiness accepts the exact release, not an
arbitrary newer Forgejo version. Forgejo is separately operated GPLv3+ software;
retain its license/source obligations when distributing the upstream image or
modifications. [Upstream installation](https://forgejo.org/docs/latest/admin/installation/docker/),
[license/source information](https://forgejo.org/faq/#is-forgejo-licensed-under-the-gpl).

## Kubernetes

Use the existing chart with `deploy/helm/golf/values-forgejo.yaml` in a **new
release with fresh databases/PVCs**, supplying a built Golf image, public origins,
existing Secret and unique `forge.instanceID`. Helm retains `gitea.*` value and
resource names for storage compatibility. They do not select the server product;
`forge.kind` does. The profile pins the Forgejo digest and sets its native
`FORGEJO__…` environment keys. `GITEA_APP_INI` explicitly retains the chart's
separate configuration mount.

An upgrade to Forgejo is rejected unless Helm can observe that the existing Golf
Deployment is already configured for Forgejo. Server-side identity checks still
apply. Offline Helm lint/render checks pass; a real Kubernetes rollout, storage
recovery and ingress/SSH/OAuth acceptance remain required.

## Selected repository staging

`scripts/forgejo-migrate.py` implements `plan`, `export`, `import`, `verify`, and
`status` for **quarantined staging**. It cannot cut over an installation. Source
and target tokens use `GOLF_MIGRATION_SOURCE_TOKEN` and
`GOLF_MIGRATION_TARGET_TOKEN`. Remote origins require HTTPS; HTTP is confined to
loopback. The target must be able to reach the source's configured public origin.

```sh
python3 scripts/forgejo-migrate.py plan --journal /private/transfer.json \
  --source https://old.example.com --target https://new.example.com \
  --repository alice/project --owner alice
python3 scripts/forgejo-migrate.py export --journal /private/transfer.json \
  --archive /private/inventory.age --recipient AGE_RECIPIENT
python3 scripts/forgejo-migrate.py import --journal /private/transfer.json \
  --source-frozen --target-quarantined
python3 scripts/forgejo-migrate.py verify --journal /private/transfer.json
python3 scripts/forgejo-migrate.py status --journal /private/transfer.json
```

The freeze/quarantine switches attest that the operator actually disabled writers,
mail, hooks, runners and external access; they do not implement those controls.
The exporter captures encrypted API inventory, including visible discussion/review
data. It is not a complete Git/LFS/package or whole-stack backup. Private reviews
belonging to other users are not inferred absent from one actor's view.

The importer writes intent before calling the supported native migration API,
uses a private destination and unique operation marker, and reconciles an uncertain
response without automatically replaying creation. Pagination, response sizes,
redirects, target identity and source inventory changes are bounded/checked. The
journal has owner-only permissions and a separate exclusive lock. Reconciliation
reports retain mismatches; every report currently has `cutoverAllowed: false`.
`verify` exits with status 3 while cutover blockers remain; a completed staging
reconciliation is not approval to switch traffic.

**Observed blocker:** the real Gitea 1.27.3 → Forgejo 15.0.9 fixture retained Git
branches, issue/PR content, labels and milestones, but one private pending review
became zero pending reviews. No source installation can be cut over on this
importer's success response alone. Review/identity mapping, dates/authorship,
all refs/LFS/wiki/packages, effective permissions and coordinated recovery need
their own transfer and verification work. No timestamp, author or approval is
synthesized to make the report pass.

## Repeatable checks and remaining gates

```sh
make forgejo-qualify
python3 scripts/forgejo-qualify.py --integration --migration \
  --output .tmp/forgejo-proof/receipt.json
python3 scripts/forgejo-migrate-test.py
python3 scripts/forgejo-inventory.py \
  --target .tmp/forgejo-proof/forgejo-openapi.json \
  --output .tmp/forgejo-proof/inventory.json
python3 deploy/helm/golf/check.py
```

The harness creates random loopback ports, isolated databases and disposable
users, then removes its containers/volumes/network. Integration defaults to the
affected configuration/identity/credential tests; `--test-pattern .` requests the
full historical suite. The current full historical PostgreSQL suite does not
pass: its old OAuth downgrade test encounters the intentional migration092
no-downgrade guard, and the broad run was stopped during lengthy schema cleanup.
Focused PostgreSQL/race and final non-database Go tests pass.

The maintained CI harness also supports `--forge-kind forgejo`; actual passing
and failing `.forgejo` Actions/GitLab-format jobs, restart persistence, once-only
dispatch, logs, cancellation, policy revocation and owned-resource cleanup passed
with the existing pinned runner. This is the bounded shell execution profile,
not general native Forgejo Actions/Runner parity.

The [API inventory](compatibility/forgejo-inventory.json) records 410 common
method/path pairs, 72 Gitea-only pairs and 81 Forgejo-only pairs. Common paths still
need field/role/behavior checks. Missing paths include Gitea's repository-license
index and several newer collaboration/admin APIs; absence cannot be translated
into a successful empty result. Full API parity, remote installation attestation,
all-user mapping, recovery, Kubernetes runtime, performance/load comparisons,
production cutover and Gitea retirement are still open. The separate native
Cloudflare checks pass; no Cloudflare infrastructure was allocated for this work.
