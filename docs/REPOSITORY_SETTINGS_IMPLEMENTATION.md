# Complete repository settings

The requested completion condition is that every repository Settings section is implemented, configurable at the appropriate permission level, enforced by its actual consumers, and qualified. The ten rows currently shown at `/OWNER/REPO/settings` are requirements, not a substitute for implementation. This applies to personal and organization repositories on both infrastructure tracks. A native feature, saved credential, inspector result or passing UI fixture alone does not establish readiness.

## Readiness and presentation

Separate three facts: implemented capability, the viewer's administration permission, and this installation/repository's configuration. A supported but disabled feature remains configurable; an absent required worker, grant or destination explains the configuration needed. Neither a disabled feature nor permission denial should masquerade as an unimplemented feature. Report provider outages and uncertain observations independently.

Replace hard-coded coverage declarations with service-backed observations as consumers ship. Resolve immutable repository and owner IDs, current native authority and inherited Golf policies. Recheck after waits and before saves. An instance administrator does not automatically own a repository or its private agent transcripts. Show effective policy and its source, current values/inventories, explicit Add/Edit actions, named connections and active bindings. Use shared TanStack forms/tables and global styles; sustained administration lives on full pages. Short confirmations may use dialogs. Live invalidations refresh reads without discarding unsaved edits; revoked authority clears private content.

`Ready` requires the complete promised section below, with evidence linked in the implementation ledger. Intermediate slices remain `Partial`; do not silently remove unmet requirements or relabel them to turn the table green. Cloudflare-specific destinations are optional implementations of the same generic capability. Readiness must not require a paid model or Cloudflare account for the portable core.

General configuration now has actual pinned-native save/readback, archive/rename/replacement fences and twelve served dark/light desktop/mobile captures in the implementation ledger. Its coverage can report Ready only with a verified current service observation. This completes that configuration row; it does not close the independent wiki workspace, the other nine rows or broader release/track acceptance.

## Delivery order

1. **RS-Settings-1: current values and access foundations.** Correct stale coverage prose and actionable links; ship native deploy-key management and qualified metadata controls. Add per-section current authority/configuration observations. Complete invitations and organization/team exposure rather than treating direct collaborator grants as the entire section.
2. **RS-Settings-2: durable execution and agent controls.** Finish the Actions engine adapter, named runner pools/resource limits and private agent conversation journal, followed by interactive turns/session recovery. Expand actual harness qualification and event assignment. Share the domain policy between browser, API, CLI and MCP.
3. **RS-Settings-3: credential and delivery consumers.** Implement scoped variables/secrets and qualified identity issuance; outbound webhooks and email delivery with real workers and history. Integrate consumer admission before presenting active controls. Connection switching pins new work to immutable versions without silently migrating old work.
4. **RS-Settings-4: governance and integration.** Resolve P0.8 target-side fencing and trusted checks; implement review/ruleset policy and merge/squash/rebase under the qualified managed boundary. Complete runner/fork/producer sharing controls and organization inheritance.
5. **RS-Settings-5: environments and lifecycle.** Implement protected previews, portable/Cloudflare deployment targets, exact artifact promotion, rollback, DNS and cleanup; add archive/transfer/delete with durable uncertainty/reconciliation and fencing of active work.
6. **RS-Settings-6: full acceptance.** Exercise every row's read/save/use/revoke/restart/recovery and role matrix on fresh Compose, Kubernetes and each qualified Cloudflare adapter. Re-run affected served screenshots, keyboard/deep-link/history and mobile checks. Record exact source/runtime/fixture/cleanup evidence; review every row before marking all ten Ready.

These dependencies permit disjoint work in parallel; they do not relax the final acceptance condition. Existing shell-CI, scoped access and final-result agent qualifications remain useful evidence for their actual scope.
