# Inline review implementation design

Prepared 2026-10-03 from read baseline `b99de7a`, updated after IR-1 exact comparison qualification. **IR-1 is implemented and bounded read-qualified; IR-2–IR-8 remain proposed work, not an implemented or qualified write contract.** The shared portable/Cloudflare core must deliver the complete human and agent review lifecycle without requiring AI or Cloudflare. This document advances GX-3/GX-4 in the [repository parity workstream](REPOSITORY_EXPERIENCE_PARITY.md); it does not close P0.8 or replace the [implementation plan](../GOLF_IMPLEMENTATION_PLAN.md).

Current evidence: [bounded inline reads](PULL_REVIEW_COMMENTS_READ_CONTRACT.md), [actual native behavior](PULL_REVIEW_COMMENTS_NATIVE_QUALIFICATION.md), [overall review mutations](PULL_REVIEW_MUTATION_CONTRACT.md), [PR comparisons](PULL_DIFF_CONTRACT.md), [shared diff presentation](DIFF_WORKSPACE_CONTRACT.md), and [implementation status](IMPLEMENTATION_STATUS.md). Read-only own-PENDING inspection, the b99de7a 434-test/native read proof, and the later 443-test exact-comparison/responsive packet do not establish inline authoring, persisted drafts, replies, thread resolution or suggestions. The new served private-fork comparison proof passed before the shared responsive-toolbar correction; the global toolbar correction passes 443 browser tests and six focused 1280/390/320px cases; replacement-image served recapture passes on `sha256:1f81b70aec461e5d2591ffb58ab17ede5f1b13fa07e18e97b60bb29a12d47017`.

## 1. Decisions and immediate work packet

Use the existing Go/Connect API, PostgreSQL/sqlc, keyring, supported forge APIs, TanStack controls and shared diff/Markdown/CSS. No new workflow engine, Cloudflare coordinator, general proxy or direct forge storage writes are needed for the first packet. The same contracts apply to both infrastructure tracks.

The **next implementation packet is IR-2: server-validated coordinates and encrypted owner-only drafts retaining the original exact comparison**. IR-1 already extends the existing diff read with caller-selected native repository/PR IDs and actual merge-base metadata, without authoring buttons or native mutation. The supported private-fork/Git/API/UI/CLI/MCP comparison qualification passed with fixture cleanup. Server coordinate validation is still required before the first writer. Then implement one bounded human batch from that selection, with encrypted owner-only draft persistence and conservative outcomes. This initial writer covers single displayed old/new hunk lines only. Native draft lifecycle, replies, edit/delete, resolution, multiline/whole-file comments and suggestions are subsequent required packets, rather than substituted ordinary PR comments or disconnected mock interfaces.

The [IR-2 draft API proposal](INLINE_REVIEW_DRAFT_API_PROPOSAL.md) specifies the proposed three-RPC private SQL-only save/reopen/edit/delete contract, exact first capture versus retained comparison, CAS/operation receipts, transport/content bounds and shared editor/privacy requirements. It is not implemented; native publication/decisions and shared repository draft events are excluded. Assign the draft migration after preceding work lands.

### Historical b99de7a gaps addressed by IR-1 and remaining source authority

- At this baseline, `GetPullRequestDiff` accepts repository address, PR number and selected base/head SHAs. Its response `base_commit_id` is the selected **base branch tip**; its native text is a merge-base diff. It observes native IDs around the read, but has no caller-expected repository/PR IDs and exposes no verified merge-base identity. See [server code](../internal/server/diffs.go) and [wire contract](../api/golf/v1/golf.proto).
- At this baseline, `forgePull` drops native `merge_base`. The pinned [PR schema](https://github.com/go-gitea/gitea/blob/v1.27.3/modules/structs/pull.go) exposes that field. Preserve and validate it; do not infer it from the base tip, a comment's blame commit or an empty original commit. IR-1 now maps/validates that field; native characterization proves the serial same-repository case, and served comparison proof separately establishes base-only reading of a renamed private fork without general source access. Private-fork authoring and in-flight moving-ref admission remain unqualified.
- Source `GetContents` returns selected commit/path and file metadata without caller-expected native repository IDs. A source read requires its own authority. The existing private-fork PR diff permission does not grant source-repository credentials or every raw-file route. Extend a qualified source boundary when needed; do not broaden fork access silently.

The [new native write characterization](PULL_INLINE_WRITE_NATIVE_QUALIFICATION.md) independently proves additional hazards: the [review handler](https://github.com/go-gitea/gitea/blob/v1.27.3/routers/api/v1/repo/pull_review.go) creates batch comments before submission, and its submit-existing-review route selects the current head. The [comment service](https://github.com/go-gitea/gitea/blob/v1.27.3/services/pull/review.go) can build retained context using current PR head/merge base even when a review records a supplied commit. Actual native tests retained a historical review header while storing newer hunk context, rebound an existing pending header on append/submit, and left pending children after dispatched 500 and 422 responses. A known hidden pending parent accepted another actor’s reply and author resolution despite 404 on reads. The probe exited 0 and purged all five users/repository; these are serial same-repository observations, not a Golf writer or an effective-write fence. Preflight and a matching review header alone cannot prove every child's original context.

## 2. Immutable authoring comparison and coordinates

Implemented packet IR-1 extends **existing** `GetPullRequestDiff`: require repository address, positive decimal native `repository_id`/`pull_request_id`, PR number and full selected base/head SHAs. Response binds those IDs plus `merge_base_commit_id`; `base_commit_id` retains its branch-tip meaning. `PullRequest.merge_base_commit_id` may be empty for unavailable metadata, but an accepted diff requires a valid nonempty value and exact retained head identity before/after. The browser compares response IDs/merge base with the displayed PR, conceals stale content and requires refresh after drift. No authoring control is enabled by this metadata packet.

In IR-2/IR-3, draft save additionally freezes displayed revision, old object and SHA-256 of the exact shown bytes. Reuse those read helpers to revalidate that selection and parse coordinates before saving; do not introduce a parallel comparison engine. Save returns an actor-bound immutable comparison identity with these separately named fields:

| Binding | Required meaning |
| --- | --- |
| Target / PR / source identities | Forge identity, target native repository ID, PR ID/number and head/base repository IDs; addresses are routing metadata. |
| `base_tip_commit_id` | Selected base branch tip, used for freshness checks. |
| `old_commit_id` | Independently observed/qualified merge-base object used by the old side. |
| `head_commit_id` | Selected reviewed head, used by the new side. |
| `diff_sha256`, parser version | Exact accepted native bytes and deterministic coordinate interpretation. |
| Entry/coordinate identity | Stable native inventory index, literal old/new paths, hunk identity, side, file line and context fingerprint. |

Server validation is authoritative. Reuse the browser parser's tested corpus when implementing a small Go counterpart; do not trust a client row number or parse the DOM. A valid single-line selection must resolve uniquely to a supported file/hunk/side in the accepted comparison. Additions permit new side, deletions old side, and context rows the explicitly chosen side. Reject ambiguous duplicate entries, invalid hunks, binary/submodule/metadata-only rows, malformed quoted paths, unsafe literal paths, noninteger/out-of-range lines and structured-preview overflow. Retain the current 512KiB raw diff / 500-file / 12,000-row bounds; raw fallback remains readable but does not become a guessed authoring surface.

Before enabling an old-side control, qualify native path semantics for renamed/deleted files against the old merge-base object. A verified new-side selection must not imply verified old-side support. Additional context requires a separate immutable source-object read with exact native identity and authority; never use branch names, today's base tip or a blame commit to expand an old comparison.

Persist the original comparison when a draft is saved so reopening after a push shows the same review context. Current access remains mandatory to serve retained private bytes. If the current comparison changes, preserve the original draft, label it earlier, and require an explicit new comparison/remap action. Remapping creates a new draft version with displayed evidence and user confirmation; it never silently changes a line, body or reviewed head. For externally authored reviews without established original base/head context, retain literal coordinates/hunks until an exact mapping can be proven.

## 3. Draft persistence and proposed API

Golf owns its server-persisted working draft; native PENDING remains a real, separately observed forge object. Label their states distinctly. Saving a Golf draft is not native publication, and a Golf draft cannot be displayed as an existing native PENDING review without verified native IDs. Full native pending creation, adoption, submission and discard remain required in packet IR-4 below.

Proposed procedures are additive; the existing zero-inline `CreatePullRequestReview` contract and journal034 stay unchanged:

| Procedure | Required binding / result |
| --- | --- |
| Existing `GetPullRequestDiff` extension | Required native target IDs; returns those IDs and actual merge base, preserving branch-tip/head fields. |
| `Get/Save/DeletePullRequestReviewDraft` | Owner, target IDs, shown comparison/digest, draft ID and expected version; first save validates/retains the exact comparison; later save returns a new version or explicit conflict. Delete affects an unpublished Golf draft, not native history. |
| `PublishPullRequestReviewDraft` | Draft ID/version, comparison ID, exact native selection, decision, canonical UUIDv4 operation key; immutable version supplies summary and ordered entries. |
| `GetPullRequestInlineReviewMutation` | Owner/key metadata inspection; current-authorized review/children only when their original binding is independently verified. |
| Native draft operations | Explicit create/synchronize/adopt/submit/discard on an exact owner review ID and revision; only after route-specific qualification. |
| Reply / update / delete / resolve operations | Exact target, owning visible review, selected comment ID/revision and operation key; separate operation classes, not a generic native write proxy. |

For the first writer choose at most 20 entries, each non-whitespace body at most 6000 UTF-8 bytes, existing 6000-byte summary limits and an explicit aggregate ceiling. These are proposed Golf bounds, not qualified native maxima. Require a nonempty summary for COMMENT/REQUEST_CHANGES initially, preserving current overall-review rules; qualify comment-only batches separately before offering that behavior. Approval remains unavailable to PR authors and on observed draft/closed/merged PRs. Inline authoring on closed/merged PRs needs its own native proof; body-only COMMENT support does not establish it.

Browser mutations retain managed-session, exact Origin and native permission checks. Every draft read/save rechecks current target access, stable forge mapping and ownership; an instance administrator does not automatically read another user's private working draft. SQL/API conflicts must preserve the local unsaved version rather than overwrite another device's save. Publication atomically freezes one immutable version before any native call; later edits require a new version and cannot modify the accepted intent.

### Concrete database work

Assign the next migration number at implementation time. Proposed tables and constraints:

| Table | Purpose and guards |
| --- | --- |
| `golf_pull_review_comparisons` | Actor/forge/native target IDs, full base-tip/old/head objects, parser/diff fingerprints and encrypted retained comparison. Immutable identity, bounded retention and current-authority reads. |
| `golf_pull_review_drafts` + `_versions` | Stable owner/target/comparison; mutable current-version/status pointer with optimistic CAS; append-only bounded encrypted content versions. An accepted publication freezes its referenced version. |
| `golf_inline_review_mutations` + `_entries` + `_events` | Unique owner/key, operation class, immutable version/selection/exact-input fingerprint, native receipt IDs, per-entry observations, effect/failure classification and append-only events. SQL forbids terminal/identity/receipt replacement and event deletion. |
| Actor/PR mutation exclusion | Durable conflict record for a forge actor/native PR, shared by inline publication/native-draft operations and overall-review admission. Unknown effect holds it; process or lease timeout never releases it. |

Encrypt paths, text, source context and draft summaries with an explicit new review-content domain in the existing AES-GCM keyring. The current domain allowlist must be extended deliberately; do not reuse infrastructure credentials' domain. Associated data binds key label, owner/forge/target, comparison, draft and version. Include the new domain in rotation, inventories and restore validation. Do not put bodies/paths/context into journals, logs, audit payloads, browser storage or command arguments. Retention can purge encrypted abandoned content while keeping minimum immutable effect metadata; accepted/unknown operations need retained verification evidence under a documented policy. A content purge must never make an uncertain key reusable.

## 4. One native batch and conservative external outcomes

Use the existing review journal pattern for durable reservation, but give inline operations their own effect contract. Native creation is nontransactional, so the overall writer's HTTP rejection whitelist must not be copied blindly.

1. Validate/freeze exact draft version and comparison. Recheck current managed actor, IDs/revision/objects, decision eligibility, native permissions and every coordinate. Scan complete bounded native review pages using the configured-span helper, including empty filtered pages. Refuse any unrelated own PENDING draft or unresolved overlapping operation. A Golf exclusion record orders Golf writers; it does not fence direct native/background writers.
2. Commit owner/key reservation, immutable entry fingerprints and conflict record before dispatch. Same key/input only inspects; changed input fails. A different key cannot bypass the same actor/PR's unknown operation.
3. Only the reservation-inserting invocation may send one `POST /pulls/N/reviews` with explicit chosen commit and the complete frozen `comments` batch. No per-entry POST fallback, request retry or background replay. Record dispatch intent before the call. Caller cancellation after possible acceptance is an inspection request, not proof of cancellation.
4. Validate the native review receipt and retain its observed ID durably while outcome remains unknown. Independently read the bound review and entire bounded child collection through current authority. Match original author/review/PR/head, decision/summary, exact entry count and the full multiset of path/side/line/body fingerprints. Check stored context against the qualified original objects; native child blame need not equal reviewed head. Reordering cannot defeat matching, and duplicate identical entries require multiplicity without inventing an entry-to-native-ID correspondence.
5. Record success only after the entire intended batch is independently verified. Success is historical submission for the original comparison, not current eligible approval or merge readiness. Child IDs and qualified context provenance bind later reads even after dismissal/head movement.
6. Known pre-dispatch refusal can be REJECTED. Any possible accepted write followed by timeout, cancellation, malformed/lost receipt, partial pending batch, extra absorbed draft, mismatched context, SQL loss or lost authority stays OUTCOME_UNKNOWN with a bounded reason. Even HTTP 422 can follow earlier child creation; no-effect rejection needs route-specific proof. A missing receipt cannot be replaced by searching for similar body text.
7. Show status/observed partial evidence without publishing the remainder. Unknown is not retried, adopted by guess, changed into success by an unrelated review, or cleared by a new browser/device/key. Reconciliation and cleanup require exact correlated native IDs, current authority, evidence that the original writer cannot resume and an explicit operation; no automatic DELETE/rollback of a possibly shared pending review.

Track effect observations separately from terminal result: dispatch uncertain, partial native draft observed, mismatched publication observed, complete batch verified. The familiar UNKNOWN/SUCCEEDED/REJECTED API states remain usable; do not turn partial evidence into a fourth fictional success. HTTP receipt/readback cannot remove effective-write race limitations. Full protection follows the separate [protected merge/admission design](PROTECTED_MERGE_IMPLEMENTATION_DESIGN.md).

## 5. Native pending lifecycle, replies and resolution

Native PENDING support must retain exact own review ID, original comparison and complete known child inventory. Explicit adoption of an independently visible own draft is not reconciliation of an unknown Golf publication. Require an inspectable provenance path; unknown old-side base cannot be invented from today's PR. Freeze/verify native inventory before submit/discard, refuse another user's PENDING even for a Golf administrator, and preserve draft data after denied/uncertain operations.

Qualify both existing-review submit and explicit-commit creation when consuming an own pending review. The former's current-head behavior cannot silently retarget a saved review. If the supported API cannot preserve the selected comparison under concurrent head/base movement, expose that exact block and pursue a supported upstream extension or the separately qualified admission boundary. Do not pretend that pre/post checks are atomic. Native append/edit/discard also need once-only receipts and partial-state handling; deleting a whole review is not a substitute for deleting one draft entry.

For a reply, bind repository/PR/review/parent-comment IDs and the original parent observation. Before any POST, independently read a **currently visible** owning review and find the exact parent in its complete collection. A known comment ID or native write permission is insufficient: the existing native probe proves replies can append to a hidden foreign PENDING parent. Initial replies target published visible reviews; own-draft reply semantics need a separate explicit choice/proof. Recheck visibility/authority around dispatch and readback, record the chosen parent relation for Golf-originated replies, and keep uncertainty if visibility changes after acceptance.

The native receipt exposes no reply parent ID. Store a Golf-originated parent relation only with the frozen request and verified receipt; externally created comments at the same path/line remain a flat location group with unknown ancestry. Ancestry loss after import/recovery must be visible, not guessed from chronology.

Resolve/reopen acts on one bound comment using its observed resolver state/revision and native authority. A deleted resolver still means resolved. Label **Resolve comment** until complete conversation semantics are qualified. A UI thread group cannot claim resolved because one same-line parent is marked; a multi-comment operation must specify every ID, preserve each outcome and tolerate partial failure. Required unresolved-conversation policy remains separate protected evidence. Published edit/delete and dismissal similarly need exact revisions, native role/visibility qualification and irreversible/unknown outcome treatment.

## 6. Shared UI, privacy and agent parity

Extend `DiffViewer`, `PullReviewComposer` and `PullReviewComments`; keep Conversation and Files changed on the same selection/draft/query primitives. Add-line controls open a compact row/workspace editor on request, with shared TanStack Form, Write/Preview, explicit Save/Cancel and a pending-entry inventory. Use shared DataTable only where an actual searchable/sortable inventory is helpful, not for comment threads. Global CSS supplies density/themes; no page-specific form/table engine or settings modal.

Preserve native stable file indices, exact old/new anchors, unified/split parity, focused row reveal and keyboard Add/Edit/Save/Cancel/Escape behavior. A selected line must remain understandable without hover, colour or pointer input. Keep constant PR tabs stable during revalidation while hiding private title/body/editor/diff; freeze accepted drafts and show original/current selection differences. Cancel private reads synchronously on closure/selection/account change, reject late generations, and immediately unmount/purge on sign-out, 401 or live access denial. Persistent drafts remain server-side; tab storage retains operation metadata only. Errors, refresh and status-only resume never auto-post.

Golf-owned successful mutations append existing repository activity/outbox events in the same metadata transaction as finalization. Events contain topic/identity/cursor metadata, not private bodies. Direct native edits may emit no Golf event: retain the explicit inline refresh button **without** the hidden-while-live `manual-refresh` class. Automatic external-edit reconciliation is a separate bounded polling/intake task, not an inferred guarantee of SSE.

Generate API, CLI and MCP parity from these exact contracts. The current 23-tool MCP catalogue and API credentials remain read-only; do not unlock writes by forging a browser Origin or presenting an ordinary PAT as a newly approved grant. Add an explicit owner-issued review-write delegation with immutable repository selection, expiry/revocation and current native/organization authority. Separate cookie+Origin browser admission from deliberately authenticated programmatic admission. CLI reads/status/draft commands take exact IDs; publication consumes a user-approved frozen draft and stable key, with private input via stdin/restrictive files. MCP write tools need the same scoped grant and explicit caller intent, not instructions embedded in untrusted repository text. Agent, executing actor and independent approving principal remain distinct; an author-sponsored agent does not satisfy independent review policy.

## 7. Required richer capabilities and native qualification

All Golf write capabilities below remain pending. The linked native characterization proves a bounded subset of the hazard cases; the remaining acceptance criteria still require evidence. Add to the existing native probe corpus rather than infer compatibility from route names:

| Capability / hazard | Required actual evidence |
| --- | --- |
| Exact comparison | Diverged base tip versus merge base; 40/64-character object IDs; renamed/deleted paths, duplicate/quoted/Unicode names, context/deletion/addition, invalid/oversized diff. |
| Fork authority | Base-only PR reviewer, independently denied source read, retained/deleted source, no leaked source credential or broadened object route. |
| Moving head/base | Chosen historical head, changing merge base, paused accepted creation/submit, stored hunk versus reviewed objects; extra/changed context stays unknown. |
| Native pending | Save/append/reload/edit/delete/discard/submit, explicit-commit versus current-head behavior, changed inventory, foreign hidden drafts, body-only absorption and concurrent own draft. |
| Partial batch | Failure on later child or final submit, lost200/SQL receipt, partial native PENDING, once-only replay/new-key denial and explicit non-replaying inspection. |
| Replies / resolution | Visible parent versus known hidden PENDING ID, wrong PR/review, reader/author/writer/admin scopes, same-line mixed resolution, deleted actors, concurrent edits and 204 loss. |
| Multiline / whole-file | Actual supported request/receipt coordinates and ranges. Two positive side inputs are not a range; line0 is not automatically a whole-file comment. Require supported upstream extension if absent. |
| Suggestions | Native Markdown/display/storage behavior plus a separately journaled exact-old-blob/expected-branch-head apply commit, authority, conflict, encoding/EOL and concurrency proof. No arbitrary command execution or fabricated native apply support. |
| Published edit/delete/dismiss | Supported endpoint, exact identity/revision/ownership, pending privacy, irreversible/uncertain outcome and complete readback. |

The [native write characterization](PULL_INLINE_WRITE_NATIVE_QUALIFICATION.md) passed against Gitea 1.27.3 with fixture cleanup. It covers serial diverged-base context, explicit historical head, pending append/submit, partial 500/422 batches and hidden-parent writes. It does not qualify a Golf writer, private-fork authoring, an in-flight head/base/pending race, lost transport or a target-side admission fence. Range/file/suggestion metadata must round-trip through Golf and import/export without claiming nonexistent native fields. Full native interoperability requires a supported provider contract; a plain comment that describes a range does not satisfy it.
