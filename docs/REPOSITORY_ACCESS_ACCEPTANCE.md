## Current observation contract for the parent implementation

Reuse existing APIs and their authority rules; readiness must not perform writes, native grants or Git pushes.

- Load independent repository metadata, then `RepositoryAccessService.GetRepositoryAccess`. Compare returned `repositoryId` with that metadata, owner ID/login with the selected owner, valid revision and recognized current effective permission. This request currently takes only the repository key; the consumer must not treat its returned ID as already caller-bound.
- Bind `ListRepositoryCollaborators`, `ResolveRepositoryCollaborator` and operation inspection to the exact repository/owner/access revision. These are administration observations, not necessary private fanout for every reader of the coverage table.
- On organization targets, `ListRepositoryTeamAccess` separately supplies `canManage`, protected team metadata and paging. A direct administrator can administer grants/keys while only a current organization owner can attach/detach teams. Do not collapse these into one permission bit.
- `ListRepositoryInvitations` supplies current `canManage` and `localIssuerAvailable`; the latter explains why a managed OAuth-only account cannot issue this explicitly delegated local-credential invitation. The own inbox remains a separate recipient-authorized page.
- `ListRepositoryDeployKeys` binds exact repository/owner/access revision and native paging. No key body needs to enter a coverage observation. An empty valid list is an available feature, not an unsupported installation.
- Add an explicit, bounded build capability observation only if the parent needs one response for the settings table: supported direct-grant, invitation, team-association and deploy-key contracts; current authority per action; local issuer availability; archive/mirror read-only configuration; exact IDs/revision; observation status. Identify the pinned qualified native/profile contract separately. An authenticated successful read verifies **current configuration/authority**, not historical test execution or recovery completion.
- Keep qualification provenance in the ledger/build release evidence. A static `implemented=true` alone cannot establish qualified Ready. Conversely, `canManage=false`, an empty inventory or deliberate read-only configuration must not mark an implemented feature unimplemented. During refresh show checking; on private denial clear values/actions; on provider failure expose observation unavailable without consuming cached success as fresh proof.
