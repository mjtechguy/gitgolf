# Named runner pools and repository placement — source packet 050

This packet provides named inventories and versioned placement for **already operator-enrolled local Docker workflow runners**. A pool label does not enroll a machine or grant authority. This first implementation has no Kubernetes, Cloudflare, agent-task placement, OS selection, network policy or CPU/memory resource contract. Capacity counts concurrent workflow attempts; it does not count matrix jobs or provide a hardware limit. The full Runners settings acceptance remains open.

## Wire and authority

`RunnerPoolService` has four browser-only RPCs: `ListRunnerPools`, `SaveRunnerPool`, `GetRepositoryRunnerPlacement`, and `SetRepositoryRunnerPlacement`. Register these with the existing managed browser/Origin/no-store boundary. **Do not add them to the API bearer or MCP read/write allowlists.**

An instance pool has an immutable UUIDv4 `id`, operator name, monotonically increasing canonical decimal `version`, runtime `local-docker`, `ACTIVE`/`DRAINING` state, `maxParallelAttempts` from 1 to 100, a sorted unique list of up to 100 configured worker identities, and `repositoryAssignmentEnabled`. There are at most 20 pools. ACTIVE requires a member; an idle DRAINING pool may retain zero members. Each worker belongs to at most one pool. Pool saves are explicit CAS mutations, with current local-password confirmation and existing Golf instance-admin authorization. They cannot use native site-administrator status as a substitute. Terminally revoked workers cannot join or remain selected in a save; an active attempt prevents joining/leaving a pool. Keeping existing membership while draining or editing capacity is allowed.

`repositoryAssignmentEnabled` is an explicit **all-repository eligibility opt-in**. It lets an ordinary current repository administrator select that pool; it grants no repository access and exposes no private repository inventory. Eligible pool metadata deliberately excludes `activeAttemptCount`; that aggregate is available only in the instance inventory. The repository inventory may describe a draining eligible pool but selection of it is refused. The selected pool is returned even if its eligibility is subsequently disabled, so a historical placement does not disappear.

Repository operations bind `RepositoryKey`, native repository ID, native owner ID and the current `RepositoryAccess.revision`. Current individual native owner/direct administrator or the existing positively proven organization-admin path is required before and after the operation. Golf global administration, native site-admin status, team-only aggregate authority and a known pool ID do not bypass that boundary. Read inspection can use a managed OAuth account. Mutation currently requires a managed local password and explicit password confirmation; the response reports `canEdit` and `passwordConfirmationAvailable` honestly.

Placement version `0` means no retained placement. An explicit bind or unbind creates version 1 or increments the existing version. Binding supplies the current pool UUID/config version; unbinding supplies empty pool/version. `RepositoryRunnerPlacement.poolVersion` is the pool version selected when the placement was saved. `selectedPool.version` is current observed configuration; those can differ. Native owner transfer is refused until an explicit transfer/rebind workflow is implemented; repository renaming is admitted only through unchanged exact native repository/owner identity and current access revision.

Both mutations are local database CAS operations, **not once-only native dispatch journals**. An error or lost response must not be interpreted as proof of no effect. Refresh current inventory/placement and inspect accepted versions; never automatically resend. Stale expected versions return `ABORTED`; known unavailable/stale admission returns `FAILED_PRECONDITION`. No secret worker key is returned. Empty draining membership is encoded as an explicit empty SQL array, never a NULL audit value.

## Queued and running work

Admission freezes pool UUID, pool configuration version and placement generation on `golf_workflow_runs`; absence/explicit unbound remains distinct through retained placement generation. These fields are immutable. New admissions observe current pool configuration while preserving the existing repository placement choice; they do not require rebinding merely because a pool version advanced.

Every pool edit, including drain/resume, increments configuration version. Every placement save increments placement generation. Existing queued work whose versions no longer match is refused at the authoritative claim fence and needs a new explicit dispatch. It is never silently rewritten or reassigned. Where membership filtering means there is no remaining candidate worker, historical queued work can remain queued but cannot run; no automatic cancellation/reassignment is promised. Existing running attempts continue through drain/configuration edits under their existing worker-control, policy, native authority, lease, source and credential fences. Worker revocation still stops execution through the existing consumer.

Unbound admissions may be claimed only by workers outside all named pools. Moving every enrolled worker into pools therefore removes legacy unbound capacity. The instance save UI must display this warning during password-confirmed changes. Unbound work is not secretly adopted by an eligible pool.

## Locking and SQL boundary

Production claim ordering is existing managed user/session/account → lifecycle/policy/broker authority → placement → worker control → pool → run. Pool save locks catalog then sorted worker controls then selected pool; it never locks placement. Placement save locks placement then selected pool. Pool state/name/capacity edits do not rewrite kept membership; add/remove only changed idle members. All locks are scoped to the configured forge and immutable IDs.

The SQL queued→running trigger is a defense against bypassed checks, not machine enrollment or authentication. A raw SQL UPDATE obtains a run row lock before trigger advisory locks. This is not the supported production claim protocol and can have inverse lock ordering; no deadlock-freedom claim is made for arbitrary SQL clients. Root qualification must exercise competing coordinated claims and relevant adversarial SQL/refusal paths before calling placement/concurrency verified. The trigger reads worker control **after** acquiring its worker advisory lock. At Read Committed, subsequent protected reads observe committed configuration after waits. Do not reuse the authoritative helper in a transaction with a previously fixed stale snapshot.

History, native identity and run pins cannot be deleted/rewritten through supported metadata mutations. Downgrade refuses any retained pool/placement/pinned history. Latest-schema recovery is not qualified by this increment.
