# Gitea exact-candidate publication and interrupted-write qualification

**Measured 2026-10-02. P0.8 remains open; ADR 0004 remains proposed.** The executable [publisher harness](../scripts/gitea-publisher-smoke.py) qualifies narrow supported primitives and reproduces unsafe behavior in an unmanaged profile. It does not implement a Golf publisher, qualify a managed deployment, or prove the complete source/base/candidate/review/policy/authority invariant. This evidence applies to the shared Gitea foundation of both tracks.

The principal result is that **an issued Gitea write can commit after the experiment changes publication authority, and a private fork can advance while a target candidate based on its old head is being received**. A durable uncertainty barrier prevents another experimental publisher from overlapping that write, but does not make the old authority current at the effective write point. An expected-base lease protects B; it does not fence source H or authority F.

## Reproduce and scope

```sh
python3 scripts/gitea-publisher-smoke.py            # unused loopback port 3020
python3 scripts/gitea-protection-smoke.py           # original proof, default port 3018
```

Requirements: Python standard library, Git, Docker Compose, and the pinned provider images. The provider-hook rendezvous requires Docker Desktop's `host.docker.internal` to reach the host; another Docker runtime needs an explicitly qualified equivalent before this particular script can be used. The callback binds an ephemeral host port, exposes only a random 256-bit path, and carries no credentials or repository contents. The provider itself is published only on loopback.

Both commands passed with exit 0 after the shared fixture refactor. The final publisher script passed twice, including the second run's additional assertion that deleted-source detail switches to the PR snapshot ref. The original protection characterization passed separately with its default custom-hooks-disabled profile. Local environment: Python 3.14.3, Git 2.39.5 (Apple Git-154), Docker Engine 29.5.2; provider version API reported 1.27.3. Observed image digests:

| Image tag used by fixture | Local image digest |
| --- | --- |
| `gitea/gitea:1.27.3-rootless` | `sha256:1c17ecaead42eb3b5391553d8708103a4beb0e86edf5b9ebc1eb269c318845f2` |
| `postgres:18.4-alpine3.24` | `sha256:9a8afca54e7861fd90fab5fdf4c42477a6b1cb7d293595148e674e0a3181de15` |

Each run creates a fresh, separately named Compose project with PostgreSQL, Gitea, private organization/repository/fork, and four ordinary identities. The bootstrap site administrator creates disposable users and enables only the fixture owner's hook permission. The publisher is a non-admin team writer explicitly allowlisted for target pushes/merges; it cannot edit branch protection or the hook. Author and owner direct target pushes are denied. Publisher operations always use the publisher's own scoped token. The author's token observes/mutates only the author's source branch; it is not used to publish the target or impersonate publisher access.

Tokens remain in process memory/environment, never command arguments or printed output. Temporary provider database passwords use the existing fixture's private `0600` environment file. Processes and HTTP exchanges have explicit bounds; fault handlers settle before repository removal. Supported API/CLI removes users, fork, repository and organization, followed by Compose removal of every dedicated container, volume and network. Normal Golf Compose and its provider settings remain unchanged. No provider database, ref file, or native hook file is read or edited directly.

## Live evidence

B is the expected target commit, H the source commit used to construct C, and F the experiment's authority epoch. Candidate publication is an ordinary authenticated Git push with `--force-with-lease=refs/heads/main:B` and the exact `C:refs/heads/main` refspec.

| Experiment | Observed result | What it establishes / does not establish |
| --- | --- | --- |
| Provider commits C but HTTP success is lost | A bounded proxy forwards the real receive request, reads the complete upstream response, then closes the client connection. The client reports failure; authenticated target readback is exactly C. | Failure to receive success is not evidence that no write occurred. This is a real provider commit with an injected response loss, not a mocked result. |
| Replacement after uncertain outcome | A fresh publisher process sees the durable issued/uncertain intent and refuses another write. Reconciliation remains uncertain without a transport-settlement signal; after settlement plus C readback it records committed. Exact replay issues no second receive POST. | The experimental admission rule conservatively preserves uncertainty. Caller-supplied settlement in this harness is not a production recovery authority. |
| Changed duplicate identity | Reusing an intent ID with changed B, C, original F, immutable repository ID, or full target ref is rejected. | Replay is bound to the stored request identity. This is not yet the full H/P/A/E product intent. |
| Issued transport survives publisher death | The proxy receives and buffers the write. The publisher process group is killed; the journal epoch advances. A replacement remains blocked. Releasing the proxy sends the already issued request and the provider commits C. | This case is explicitly **transport accepted**, not yet provider accepted when paused. Killing the publisher does not recall a request retained by another component. |
| Write paused inside actual provider | A supported pre-receive hook enters an explicit callback gate. Target readback is still B. The journal epoch advances; replacement is blocked. After release, the original request commits C under the old epoch. | Direct evidence of a **target-side authority fencing gap**: a new application epoch does not revoke an already accepted provider write. Blocking replacement prevents a second overlap; it does not prove F is current at publication. |
| Private-fork access and candidate objects | Publisher `GET /repos/{fork}` returns 404. Base PR detail nevertheless provides the correct fork ID, source ref and H, matching the author's direct source read. Publisher fetches the base repository's PR ref and obtains H. | Supported scoped access suffices to obtain this PR's candidate objects without an admin credential or blanket fork grant. Snapshot retrieval is not source reservation. |
| Exact private-fork publication and bookkeeping | Candidate parents are exactly `[B,H]`; the fetched published tree equals the prepared tree. With manual merge enabled and autodetection disabled, PR is initially unmerged; publisher's explicit manual-finalization request returns 200 and readback records `merge_commit_sha=C`. | Supported exact-C push and subsequent PR bookkeeping work for this fixture. They are separate operations, not an atomic H/B/C authorization transaction. |
| Private source changes while target is inside receive | Target hook holds C built from H1. The author starts an independent fork push; authenticated source readback becomes H2 while target remains B. After release both clients succeed, target is C with parents `[B,H1]`, and H2 is not its ancestor. | A reproduced unmanaged private-fork race. Successful characterization is a failed protected invariant, not managed enforcement success. |
| Source branch deleted | Author deletes the fork branch. Its branch API returns 404 and Git advertisement contains no source ref. PR detail still returns H2, but `head.ref` is now `refs/pull/<n>/head`. | A surviving PR SHA can represent retained objects after source deletion. Admission must require the expected source identity/ref and a live-source observation, and reject this fallback. |

The private-fork push can update its source ref before its HTTP client finishes. The successful experiment therefore starts that push separately, observes the source ref through authenticated Git, releases the target, and then joins both clients. Waiting for source response completion inside the held target interval caused an earlier bounded fixture timeout; that attempt is not counted as race evidence.

The journal is a temporary SQLite database with `BEGIN IMMEDIATE` admission and a conservative global unresolved-intent barrier. Every attempted publisher is a separate process. It is deliberately an experiment, not a production schema or concurrency service: it lacks the Golf PostgreSQL policy/approval/evidence transaction, source and policy resource reservations, scalable conflict sets, operational recovery authority, and externally enforced F. A new epoch rejects a new stale request but cannot fence the already issued request demonstrated above. No native merge queue, product capability, or availability guarantee was added.

## Provider settings and source interpretation

Only the disposable publisher profile enables `security.DISABLE_GIT_HOOKS=false`; a separately authorized fixture owner receives `allow_git_hook=true`. The bounded pre-receive script is installed and deleted through the supported Git-hook API. It contacts the random gate, waits at most 20 seconds, and exits unsuccessfully on timeout. It never examines or modifies provider files. Hooks execute with forge process authority and are not a safe feature to grant to untrusted repository authors. The normal profile remains hook-disabled. See [Gitea security configuration](https://docs.gitea.com/1.27/administration/config-cheat-sheet/#security-security) and the [pinned Git-hook API](https://github.com/go-gitea/gitea/blob/v1.27.3/routers/api/v1/repo/git_hook.go).

The pinned PR-detail converter can open the actual head repository and resolve its existing branch, while separately projecting caller-visible repository metadata. When the branch disappears, it can fall back to retained PR refs. This explains the measured private-fork and deletion outcomes; it is not a promise that every field of a native PR response represents a live authorized source. See [Gitea 1.27.3 PR conversion](https://github.com/go-gitea/gitea/blob/v1.27.3/services/convert/pull.go).

Manual merge is disabled in the default repository configuration. Fixture setup explicitly enables `allow_manual_merge` and disables `autodetect_manual_merge`, then reads both settings back. An earlier harness attempt wrongly accepted either 200 or 405 without setting this option and failed its post-state assertion; that was a corrected fixture assumption, not successful manual finalization. The final test requires 200 and exact state. See [pinned repository defaults](https://github.com/go-gitea/gitea/blob/v1.27.3/models/repo/repo_unit.go).

Manual finalization checks permissions and an existing commit's ancestry in the base, then records the merge. It does not itself assert current base equals C, unchanged fork H, exact candidate parents/tree, or current trusted review/evidence. Its manual path bypasses later general merge-readiness checks. Golf must perform its full admission and keep native bookkeeping behind that boundary. See [manual merge implementation](https://github.com/go-gitea/gitea/blob/v1.27.3/services/pull/merge.go), [merge preparation](https://github.com/go-gitea/gitea/blob/v1.27.3/services/pull/merge_prepare.go), and [merge HTTP handler](https://github.com/go-gitea/gitea/blob/v1.27.3/routers/api/v1/repo/pull.go).

An initial attempt to synchronize on Git's hook output reached the client only after completion; a target-still-B assertion rejected it. The final test uses a direct hook callback and actual ref readback instead. The callback is fault instrumentation, not a policy hook proposal. It has no review/policy/source reservation protocol and does not remedy any measured gap.

## Remaining decision and concrete next work

The experiment narrows [ADR 0004](decisions/0004-protected-integration-enforcement.md); it does not complete P0.8-PUBLISH-1. The [mutation-boundary inventory](GITEA_MUTATION_BOUNDARY_INVENTORY.md) still identifies public API/web/Git paths, OAuth exceptions, background work and owner administration outside a qualified boundary. In particular, native PR GET can schedule provider checking, so a blanket GET allowlist is not sufficient. See the [pinned PR handler](https://github.com/go-gitea/gitea/blob/v1.27.3/routers/api/v1/repo/pull.go).

1. **Decide the authority contract before implementation.** Prove a supported target-side fence or a durable authority reservation that remains authoritative until the accepted operation conclusively terminates. Advancing F while an old provider write remains accepted cannot be described as fencing. A replacement must fail closed; fault recovery may sacrifice availability, but must not silently weaken the invariant.
2. **Qualify a real managed boundary for source and target.** Deny native bypass routes and quiesce background writers, including private-fork source writes; preserve the narrow real OAuth login/consent/revocation flow. Repeat this same source race through the actual boundary and require rejection or correct ordering. If source authority is unmanaged, deny protected integration for that PR.
3. **Implement only after the boundary is viable.** Bind H/B/C/P/A/E/F and stable identities in the Golf PostgreSQL intent, preserve the actual resource reservations across uncertainty, then qualify lost-finalization recovery and manual-bookkeeping replay. Test review/membership/protection changes and native context forgery too. This SQLite experiment does not discharge those obligations.
4. **Use the ADR's supported upstream-extension fallback if those guarantees cannot be proved with unchanged Gitea.** Keep protected integration unavailable while the decision remains open; do not substitute polling, a base lease, snapshot refs, hook callbacks, or “audit after merge” for the required predicate interval.

No customer data, normal deployment, repository CI, or upstream submission was changed by this qualification.
