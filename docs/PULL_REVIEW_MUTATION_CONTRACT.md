Status: initial generated API, durable backend and served overall-review UI implemented and locally qualified on 2026-10-03. Exact evidence is recorded below and in [implementation status](IMPLEMENTATION_STATUS.md). This is a body-only human review slice for the shared portable/Cloudflare core, not full GitHub review parity or protected merge authority.

## API, input and authority

`RepositoryService.CreatePullRequestReview` takes the repository address/immutable native ID, native PR ID, repository-local PR number, displayed `expected_revision`, full lowercase base/head commits, `COMMENT`, `APPROVED` or `REQUEST_CHANGES`, exact UTF-8 `body` and canonical lowercase UUIDv4 `idempotency_key`. Review state is not a PR lifecycle state. Base/head lengths must match and be 40 or 64 characters. Body preserves whitespace and is bounded to 6000 bytes under the shared discussion-text rules; COMMENT and REQUEST_CHANGES need non-whitespace text, while APPROVED may have an empty body. PENDING, REQUEST_REVIEW and unknown events are refused before reservation.

Only current managed browser-session authority with the exact allowed Origin may dispatch. A read-only Golf API credential may inspect its issuing account's `GetPullRequestReviewMutation` metadata but cannot create a review. This increment does not add CLI/MCP review writes. Native repository token scope and current native permissions remain independently required; it does not require native issue scope just to create a review.

Preflight binds current native repository/PR IDs and the displayed revision/base/head. Approval/change requests are refused for observed draft, closed or merged PRs and for the PR author's own account. This Golf restriction on draft decisions is deliberate: the native API itself permits draft approval/change requests. COMMENT retains the separately qualified native closed/merged/self behavior. An offered review control is not advance proof that the eventual native caller has permission.

Native read-role users can submit a decision with `official=false`; writer decisions may be `official=true` under native rules. Neither field confers trusted Golf approval or merge eligibility. CODEOWNERS, required reviewer/team identity, current protection policy and exact tested candidate must be evaluated by the separate protected integration design.

## Pending drafts and pagination boundary

Before a body-only dispatch, inspect every bounded native review page for a PENDING review owned by the submitting native account. A found draft produces `pending_review` with no POST. Native creation otherwise consumes that draft and all of its inline comments even when Golf omits `comments`.

Empty visible native pages cannot end this scan: the provider counts other users' hidden pending drafts before filtering. Its `max_response_items` also clamps requested limits; actual local settings report 50, so requesting 100 does not establish a 100-row native span. The shared `withNativePageSize` observes supported `/api/v1/settings/api` before/after the read, validates a configured maximum 1–2147483647, and uses `min(requested, maximum)` for the request and completion arithmetic. It follows canonical stable unfiltered totals. Missing/malformed/drifting totals, incomplete scans, changed settings or invalid configured maximum refuse dispatch. A complete initial scan is bounded to 2000 native reviews, requiring at most 2000 review-page reads when the configured maximum is 1; normally it needs at most 40 at the current maximum 50. A 15-second child context now bounds the entire pending scan, including current authority and setting observations; expiration denies an incomplete preflight without POST. A real-PG interrupted-page test verifies cancellation leaves a durable rejection and zero POSTs. Exact 15-second budget exhaustion is not timing-qualified. Config observations are not an atomic setting lock or ABA detector.

Read-only review found a 100-request/50-native mismatch in the initial preflight and existing PR/review/comment/collaborator total-based reads. The corrected helper now wraps all four read families and pending preflight. Real-PostgreSQL regression tests pass in 17.341s, including two empty 50-row native pages followed by the caller's pending review on page 3 at total 101. Missing/negative/drifting settings unit tests also pass. Actual Golf submission and existing native pending-draft refusal now pass on the served image below. A pending draft created concurrently after preflight can still be absorbed. Both receipt and independent readback must show zero code comments for a clean body-only success; otherwise retain unknown outcome and never resend. This detects the discrepancy after the external effect, rather than preventing all concurrent native effects. Inline drafts, batched line/multiline review comments, suggestions, replies, resolution, dismissal and deletion remain separate implementation work.

## Once-only journal and external outcomes

Migration034 creates independent `golf_pull_review_mutations` and append-only event tables. Reservation stores actor/forge identity, immutable selection metadata, exact-input SHA-256 and a separate exact-body fingerprint; no plaintext review body, credential or draft is stored. The owner/key pair is unique. The reservation and RESERVED event commit before native dispatch. Only the invocation that inserted the reservation may send the native POST. Identical input/key replays inspect existing evidence; changed input with that key fails. Different keys are distinct intents, so clients must retain the original uncertain key rather than manufacture another to retry.

The one native request uses explicit selected `commit_id` and body/event, with no inline comments. A valid native200 receipt binds positive review ID, original account ID, selected PR URL, original full head, event, body fingerprint, valid timestamps, explicit zero comment count and an undismissed review. A matching provisional review ID is committed with a RECEIPT event while outcome stays unknown. Independent current-authorized `/reviews/{id}` readback must satisfy that same immutable intent before a COMPLETED success event is committed.

Journal transitions are `OUTCOME_UNKNOWN → SUCCEEDED` or `OUTCOME_UNKNOWN → REJECTED`. SQL checks/triggers prohibit identity replacement, observed-ID replacement, terminal rewrites/deletion and event mutation. A success requires an already retained receipt ID. Native protected merge or foreign journal status does not complete this review intent.

Known preflight refusal or qualified native400/401/403/404/409/412/422/423 rejection is recorded as REJECTED. Lost response, transport/provider failure outside that rejection set, malformed/mismatched receipt, absorbed code comments, post-dispatch lost authority or mismatched readback remain unknown. There is no retry, guessed adoption by body/author, background replay worker or automated reconciliation. Uncertainty can survive restart because original metadata/key remains durable; that is not exactly-once native publication.

## Snapshot and history semantics

Success means that an overall review for the originally displayed head was independently observed. It does **not** mean that head is still current. A branch may advance after POST while a matching review receipt/readback still succeeds. Native stale flags remain visible provider observations; native COMMENT can report `stale=false` for an older reviewed head. UI must label an earlier reviewed snapshot independently by comparing the review commit with its current observed PR head.

Original repository/PR/review IDs must remain bound during readback. Current access/session is rechecked around private reads; loss of repository access can leave historical own-operation metadata available without review body. Unknown/rejected outcomes never expose a guessed body. After confirmed success, a matching review later dismissed by native administration remains inspectable with `dismissed=true`; its historical journal stays SUCCEEDED. The original receipt and pre-completion readback still require an undismissed review. Real-PostgreSQL regression proof passes for this phase distinction. Changed body/identity/head/event still fails matching rather than returning unrelated review text. Historical submission does not confer current eligible approval.

Native address endpoints do not atomically require the expected repository/PR IDs, displayed revision, current head or Golf session validity at the effective write. Pre/post observations cannot cancel a native request already accepted. This operation therefore does not close P0.8, private-fork fencing, time-expiry semantics, trusted reviews/checks or conditional merge/squash/rebase.
