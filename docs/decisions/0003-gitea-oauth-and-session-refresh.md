# ADR 0003: Scoped Gitea OAuth for browser sign-in

Accepted 2026-10-01; implementation evidence is recorded in the ledger.

## Decision

Use Gitea's authorization-code grant with S256 PKCE and a registered confidential application for browser sign-in. This provides a local, portable login path without requiring Cloudflare or an external identity service. Retain explicitly labelled PAT bootstrap for the CLI and installations without OAuth configuration. This is Gitea-backed identity, not Golf local accounts or generic external OIDC.

Public authorization uses `GITEA_PUBLIC_URL`; server-side exchange uses the configured internal `GITEA_URL`. Both refer to the same trusted Gitea installation. Register exactly `${GOLF_PUBLIC_URL}/auth/gitea/callback`; no user-controlled return destination is supported. Require the client ID, client secret and public provider URL together. Production URLs require HTTPS; explicit loopback development remains the bounded exception.

Request only `write:user`, `write:repository`, `read:issue` and `read:organization`, for the current UI's repository creation/read, issue reads and member-scoped organization/team browsing. Organization reads additionally use the user scope on `/user/orgs`; `write:user` includes it. Existing provider grants lacking organization scope remain denied for these new reads and require revoking the existing Golf grant in Gitea Settings → Applications followed by new explicit consent; refresh never silently broadens a grant. Pinned Gitea can reuse a confidential client’s existing narrower grant on a new sign-in without showing consent, so re-login alone is not a scope upgrade. These route scopes include broader upstream write authority than the current Golf UI; the consent screen must make them visible. Do not request `all`, unknown scopes or OIDC-only scopes: Gitea documents that these combinations can yield full access. More restricted PAT sessions remain supported. Access is always limited by the effective user's upstream permissions.

Random state and a separate HttpOnly browser-binding cookie protect login CSRF. PostgreSQL stores their hashes, an encrypted verifier and a ten-minute expiry. Consume attempts atomically before code exchange, so replay and replica races fail closed. Authorization errors and redirects reveal no codes, state, tokens or provider error descriptions. Callback responses disable caching and referrers. Credentials never enter browser storage.

Account linkage uses the exact existing `(forge_url, forge_user_id)` key. Never link different accounts by login name or email. Successful sign-in replaces the current Golf session. OAuth access/refresh credentials are encrypted with explicit credential kind and version; old PAT ciphertext stays readable. Use bearer authorization for OAuth and token authorization for PATs, selected by kind rather than token shape.

Refresh serializes by session row and atomically persists rotated credentials. It never extends Golf's absolute twelve-hour session expiry. Transient provider failures retain recoverable state and fail visibly; invalid/revoked grants require sign-in. Pinned Gitea refresh `unauthorized_client` means an unusable refresh token and joins `invalid_grant`/`invalid_token` as terminal only on HTTP 400/401. `invalid_client` means rejected application credentials (also used for provider application lookup failures): retain the session ciphertext and return a safe operator-configuration `unavailable` error. HTTP 5xx/429 responses remain transient even if their body contains a grant error code. If rotation succeeds but identity lookup fails temporarily, persist the new encrypted credential as unverified and refuse use until the exact upstream user ID is checked. A database commit failure after provider rotation cannot undo the provider operation; it fails closed and may require sign-in. Logout invalidates the local Golf session; upstream consent management remains in Gitea. Claims about immediate upstream revocation must match the pinned provider's actual access-token behavior.

## Remaining identity work

Golf local accounts, external OIDC, organization/team roles, managed service/Git credentials, MFA/recovery and CLI device login remain separate plan requirements. This increment supplies neither an organization authorization shortcut nor an unrestricted site credential. Callback protections do not replace future installation-wide abuse controls, audited credential key rotation or production ingress qualification.

The OAuth goose downgrade deliberately deletes OAuth sessions before removing the credential-kind column; PAT sessions survive. It is not a lossless credential rollback and is not run automatically.

The OAuth protocol helper is `golang.org/x/oauth2` 0.37.0. Provider-specific error behavior is qualified against [Gitea 1.27.3 token handling](https://github.com/go-gitea/gitea/blob/v1.27.3/routers/web/auth/oauth2_provider.go), with live consent and short-lived rotation checks supplementing real PostgreSQL tests.
