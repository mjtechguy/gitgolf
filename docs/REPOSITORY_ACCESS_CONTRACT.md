# Repository access administration

Golf exposes collaborator and deploy-key management for positively identified personal and organization repositories on both infrastructure tracks through supported forge APIs. Cloudflare is optional. Organization teams retain their separate owner-authorized association controls; this slice does not change team-wide permissions, owner teams, global administration, custom roles, repository ownership, visibility or branch protection.

## Native authority and account binding

Every request uses the caller's current encrypted browser-session credential. Golf verifies the local session and immutable native caller ID before and after provider operations. Bearer credentials cannot invoke this browser administration service; same-origin checks and no-store responses apply.

The repository route must resolve to the exact expected immutable repository and owner IDs. The actual personal owner can manage access. Another account requires a current explicit collaborator membership and native effective `admin` permission, together with the repository's native admin permission. A native site administrator may report effective `owner` on another person's repository; that observation is **not** a Golf ownership grant or an override. There is no alternate privileged token.

Native user search with the immutable owner UID positively proves an individual owner. Gitea 1.27.3 restricts this search to individual users. An empty search result requires a successfully bound organization lookup to classify the owner as an organization. A hidden organization's lookup can return 404 even to a direct repository administrator; Golf fails closed rather than assuming that 404 means a personal owner. For an organization repository, Golf additionally binds the organization ID and proves current organization membership. Administration requires positive organization-owner evidence or direct collaborator membership with native effective admin permission. Effective team administration alone, Golf instance administration and native site-admin owner-level observations do not establish this authority. Native repository admin permission is also required; archived repositories and mirrors remain read-only for these mutations. The same proof is used by direct grants, deploy keys and invitation issuers. Rules inspection deliberately retains its separate read authority for archived repositories and mirrors.

The account preview resolves an existing native username, then binds its immutable user ID. The actual owner and the acting account cannot be added, changed, or removed through collaborator mutations. A target with exceptional effective `owner` permission is also read-only because this API cannot qualify a direct grant independently of that authority. Native account eligibility and token scope continue to apply.

## What the permission observation means

The inventory paginates explicit native collaborators and rechecks each immutable user identity. Each entry has a separate `isDirect` membership observation and a native effective permission (`none`, `read`, `write`, `admin`, or `owner`). Effective permission is not claimed to be the direct stored grant. Public repository readability can remain `read` after a direct collaborator is removed; removal succeeds only when explicit membership is absent. Owner and native site administrator behavior must not be inferred from the permission string alone.

Only `read`, `write`, and `admin` are writable. Users explicitly resolve and review an account before applying its grant, and confirmation is required for removal in the UI. The immutable target ID and preview revision accompany the mutation. Every separate write requires an explicit fresh review. Because the native API does not reveal the direct mode, an effective permission equal to the requested role is not treated as proof of a no-op. Absent-member removals are refused.

## Freshness, response loss, and native races

Repository and target revisions hash observed native identity and access state. Golf rechecks both, current native management authority, and the live local session immediately before a single native PUT or DELETE. A successful native 204 receipt is followed by immutable identity, membership, permission, repository, and caller-authority readback. There are no automatic write retries. A failure after dispatch can mean the operation applied. Original-operation inspection, rather than a matching inventory alone, governs whether another Golf change may be admitted; the generation increment below retains this uncertainty.

These revisions are best-effort stale-preview fences, **not atomic compare-and-swap or security locks**. Native username-addressed collaborator routes do not atomically bind an immutable ID, expected prior grant, repository owner, or caller role at dispatch. External account rename/reuse, repository transfer, permission changes, local revocation, and grants from other native writers can race the final check or readback. Golf does not claim exclusive writer ownership, transactional native role enforcement, exactly-once grants, or that effective permissions identify direct grant metadata. Atomic adapter primitives or an exclusive, qualified mutation authority remain future work.

## Organization and effective-permission source increment

This source increment enables the shared organization authority path and removes duplicated organization exclusions in the mounted collaborator/deploy-key controls. Current inventories and preview labels distinguish **direct membership** from **effective access**. Editing requires an explicit requested direct permission; the UI does not seed a guessed stored role from aggregate native permission.

The pinned native collaborator list exposes accounts and the membership route exposes direct membership. Its permission route returns aggregate effective access; it does not return the stored direct mode. An exact native PUT204 acknowledges the requested read/write/admin operation. Independent readback must bind the same recipient and show direct membership plus effective access at least as high as requested. This acknowledges the selected request, not an exclusive or atomically verified stored direct role. Removal verifies direct membership absent while preserving any effective public/team access. A missing/invalid native acknowledgement remains uncertain even if later inventory resembles the intended result. There is no automatic retry.

Invitation acceptance uses the same distinction: a lower requested direct role beneath higher inherited access is not rejected merely because the effective observation is higher. Existing native and current-session postflight fences remain required before success.

A private exact-forge/repository transaction scope can reuse an already-held shared lifecycle gate for nested native writes. The hook still resolves and validates current native identity and rechecks blocked state in that same transaction. It cannot release the caller's gate or authorize a different target. This avoids a nested shared-lock deadlock behind a queued archive-exclusive waiter.

Focused source and browser results are recorded with the increment; real PostgreSQL execution and served personal/organization role and Git-key qualification are pending parent execution. That first increment preceded the retained generation/original-operation contract below. Neither increment eliminates external native races or independently completes the Access row. ## Retained direct-grant generations and original operations (048 source increment)

`SetRepositoryCollaborator` and `RemoveRepositoryCollaborator` require a new canonical UUIDv4 `idempotencyKey` for each explicitly reviewed action. There is no legacy blind-write fallback. The private journal binds the managed actor, exact forge/repository/owner/recipient IDs, original route and login, both preview revisions, selected permission or removal, and complete request fingerprint. Reusing an actor's key with a different intent fails without dispatch. An exact existing key is status-only and never resumes native execution, even if it was stranded before dispatch.

A retained slot per forge/repository/recipient starts at generation zero and increases before each admitted direct change or invitation grant. Collaborator previews fold that generation into their revision; zero preserves the original native-only revision shape for existing 044 invitations. Acknowledged add/remove cycles cannot recreate an earlier Golf preview, including when native effective permission is unchanged beneath inherited team access. Slots and historical intents are not deleted on completion, logout, expiry, account changes or key rotation. No credential copy or new encrypted credential family is introduced.

The lock order is the established managed-user/session order, shared exact-repository lifecycle gate, then same-repository/recipient advisory transaction lock. Golf refreshes native authority, immutable IDs and preview observations after waiting. Invitation acceptance joins that same slot and compares its captured recipient revision with the current generation. Its original 044 journal remains authoritative; historical receipts are not rewritten. The 048 lifecycle aggregate wraps, rather than replaces, prior execution, invitation and email outstanding-work counts.

Direct phases are `RESERVED`, `DISPATCH_UNKNOWN`, `SUCCEEDED`, and `REJECTED`. Reservation and its generation commit before any possible native effect; dispatch uncertainty commits before the single PUT/DELETE. A known later preflight refusal can produce durable `REJECTED` without a native write. `SUCCEEDED` requires the exact native 204 acknowledgement, independent same-recipient membership/effective-permission readback, and final current managed/native authority. Native, SQL, commit, session or postflight uncertainty remains unresolved. `RESERVED` and `DISPATCH_UNKNOWN` block overlapping Golf direct changes, invitation acceptance and archive admission. They have no automatic reconciliation or force-clear action in this slice. External native/Git writers do not acquire these Golf locks; no atomic native CAS or exclusive native writer claim is made.

`GetRepositoryAccessOperation` is managed-browser-only and requires the exact original target and key. It rechecks current native administration, repository/owner identity and original repository access revision before exposing the requesting actor's journal. Other actors cannot inspect that private receipt. A success receipt contains **historical** acknowledged intent, generation, effective permission and direct-membership observations, not a fresh inventory or stored direct role. The optional fresh collaborator is absent on status-only inspection/replay. Private intents and their transitions emit no shared repository activity.

For definitively absent original keys with a known pre-reservation semantic refusal, `Golf-Access-Effect: none` permits an explicit dismissal followed by a separately reviewed new action. Existing-key fingerprint mismatch, missing/denied status, storage/native/commit ambiguity and unknown outcomes never carry that claim. The browser retains only scoped key/native IDs, revision hashes and selected permission/removal constants in session storage, before dispatch. Reload performs original-key GET inspection only; it does not repeat mutation. Malformed, inaccessible or over-cap stored metadata fails closed. Known terminal receipt inspection or a verified no-effect refusal must be explicitly finished; inventory refresh alone cannot resolve a lost acknowledgement. Auth denial hides private rows and receipt details while retaining original metadata for inspection. Logout/account changes clear other users' metadata through the application seam.
