# Bounded team membership administration

`OrganizationAdminService` manages membership in existing non-owner native teams. It neither creates organizations/teams nor changes team permissions, repository assignments, organization ownership or Golf/global roles. Read/write/admin grants already attached to a team can be broad; adding a member activates those native grants, including additive access through other teams. Removing one membership does not remove other grants or necessarily remove organization membership.

## Authority and identity

`GetTeamAdministration` requires actual current organization membership and a readable native team bound to that organization's immutable ID. It returns the typed team metadata, organization ID, a revision, owner-team state and whether the current native organization owner can manage membership. Site-administrator visibility and Golf instance administration do not substitute for native organization ownership. Current-owner proof uses the native `is_owner` field; `is_admin` alone is insufficient. Missing permission fields fail closed.

The Owners name, owner team permission or any owner-valued unit grant marks a team unavailable for membership administration. Every mutation and candidate lookup rejects such teams. This deliberately excludes ownership transfer and last-recoverable-owner problems characterized in [native role qualification](GITEA_IDENTITY_ROLE_QUALIFICATION.md). It does not claim those problems are solved.

`ResolveTeamMember` is an explicit owner-authorized preview: organization ID, team ID and expected revision are supplied with a login; the response returns the native immutable user ID and current membership state. Add/remove requests bind that exact user ID and login. Existing typed organization-team member lists remain read APIs; their contents do not themselves grant mutation authority. Membership changes require a current browser session and exact Origin; read-only API credentials cannot access this administration service. Raw provider fields such as email and site-admin flags are not copied into candidate replies.

Before dispatch, Golf rechecks current organization/team bindings and metadata, actual organization membership, native ownership, target login-to-ID binding and local session authority. After the native operation it independently verifies the target identity and expected membership, then rechecks team revision, owner authority and membership before returning success. No privileged native credential replaces the caller's credential. Native scopes independently enforce access and can deny a call for a user whose account owns the organization.

## Revision and uncertain outcomes

The revision fingerprints current organization/team identity, metadata and per-unit grants. Editing per-unit grants, visibility or team context between preview and save requires a new preview. The revision does not snapshot team repository assignments or every other team membership; these can independently change effective access, which remains native/additive authority. Adding an existing member or removing an absent member fails precondition before dispatch; changed user identity also fails precondition.

These are fresh observation checks, **not an atomic transaction or conditional native mutation**. Gitea's pinned team-member routes address usernames and do not provide a qualified immutable-user-ID/CAS primitive. Independent native administration can race the gap between Golf's final verification and dispatch, including renames, replacement accounts or changing grants. Post-verification detects observed disagreement but cannot undo a completed native mutation. This bounded increment does not close the plan's exclusive write-ownership, durable mutation journal or systemic role-policy acceptance gates, and must not be described as preventing every native race.

Golf performs one native PUT/DELETE, requires HTTP 204 and checks the membership through a separate native GET (HTTP 200 with the exact identity after addition; HTTP 404 after removal). Lost/malformed responses, mismatched post-state and authority revocation are not presented as success. The change may already have occurred. Backend and UI do not retry automatically; refresh and inspect the actual membership before another action. Cancellation cannot undo completed native changes. There is no durable operation-status record in this slice.

## Runnable qualification

`go test ./internal/server -run TestOrganizationAdmin` covers canonical input/revision validation, owner-team exclusions, malformed-body authentication/Origin checks and bearer denial. With `GOLF_TEST_DATABASE_URL`, `TestOrganizationAdminPostgres` uses real Golf session storage and a controlled provider to test exact large user IDs, owner-only access, duplicate-state denial, changed grants, membership readback, applied-before-response-loss without retries, cross-organization team rejection, ownership revocation during target lookup and session revocation before dispatch.

`scripts/organization-admin-smoke.py` tests the running Compose stack with disposable owner, ordinary member, target and outsider accounts; private organizations, non-owner teams and a private assigned repository. It verifies real API field/status shapes, owner-team/cross-organization denials, membership changes, the target's subsequent repository access and revocation, stale metadata, Origin/bearer/logout denials and cleanup. Its served-browser helper additionally exercises an explicit add editor, canceled drafts, resolved identity review, persistence after reload, confirmed/canceled removal and narrow-screen layout. No retained account or owner-team membership is changed. Native role qualification's broader additive/recovery limits remain applicable. Successful runs and exact runtime versions belong in the implementation ledger.

Primary native references: [organization permissions](https://docs.gitea.com/api/next/operations/org-get-user-permissions/), [particular team member](https://docs.gitea.com/api/operations/org-list-team-member/). Local qualification against pinned 1.27.3, rather than a newer documentation schema, determines the supported behavior.
